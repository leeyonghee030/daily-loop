## 2026-07-19 — 서비스기획 → 유저플로우 → 도메인모델 → ERD

### 오늘 한 일 (한 줄 요약)

와이어프레임을 보면서 빠진 부분들(로그인, 알림, 삭제 정책 등)을 하나씩 결정하고, 그 결정들을 **서비스기획서 → 유저플로우 → 도메인모델 → ERD** 순서로 문서화했습니다. (`docs/project-spec.md`, `docs/user-flow.md`, `docs/domain-model.md`, `docs/erd.md`)

이 4개 문서를 순서대로 만드는 이유: 기획(뭘 만들지) → 흐름(사용자가 어떻게 쓸지) → 개념(어떤 데이터가 있는지) → 실제 DB 설계, 이렇게 점점 구체화되는 순서라서 나중에 코드를 짤 때 왔다갔다 헤매지 않게 하기 위함입니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
|---|---|
| 유저플로우 (User Flow) | 사용자가 화면을 어떤 순서로 넘나드는지 그린 지도. "로그인 → 온보딩 → 홈" 같은 화살표 흐름 |
| 도메인모델 (Domain Model) | 앱 안에 어떤 "것들"(User, Routine, Diary...)이 있고 서로 어떻게 연결되는지 정리한 개념도. DB를 만들기 직전 단계의 설계 |
| ERD (Entity Relationship Diagram) | 도메인모델을 실제 데이터베이스 테이블로 옮긴 설계도. 테이블·컬럼·타입·연결관계를 그림으로 표현 |
| PK (Primary Key) | 테이블의 각 행(row)을 구분하는 고유 번호. 예: 루틴마다 다른 `id` |
| FK (Foreign Key) | 다른 테이블의 PK를 가리키는 연결고리. 예: `routines.slot_id`가 `slots.id`를 가리킴 → "이 루틴은 이 슬롯에 속한다" |
| 소프트 삭제 (Soft Delete) | 실제로 행을 지우지 않고 `deleted_at`(삭제된 시각) 컬럼만 채워서 "삭제됨" 표시. 조회할 때 이 값이 비어있는 것만 보여주면 됨. 완전 삭제보다 안전하고, 나중에 복구나 통계 분석에 쓸 수 있음 |
| UNIQUE 제약 | 특정 컬럼(조합)이 절대 중복되면 안 된다는 DB 규칙. 예: 한 유저가 "아침" 슬롯을 2개 가질 수 없음 |
| Partial Unique Index | 조건부 UNIQUE. 예: "삭제되지 않은 것들 중에서만" 날짜당 일기 1개 — 소프트 삭제와 "하루 1개" 규칙을 동시에 만족시키기 위해 씀 |
| CHECK 제약 | 컬럼 값이 특정 조건을 만족해야만 저장 가능하게 강제. 예: 루틴은 "정확한 시각"과 "슬롯" 중 반드시 하나만 있어야 함 |
| RLS (Row Level Security) | Supabase가 제공하는 DB 레벨 보안 기능. "내 데이터는 나만 조회/수정 가능"하게 서버가 자동으로 막아줌. 아직 우리 프로젝트엔 미적용 상태 (구현 전 확정 필요 항목으로 남겨둠) |

### 오늘 확정한 결정 요약

- **인증**: 구글 로그인 + 카카오 로그인 둘 다 지원
- **삭제 정책**: 전부 소프트 삭제
- **슬롯**: 시간 커스텀 가능 + 슬롯별 알림 on/off 토글 추가
- **알림(FCM)**: 블록 알림(슬롯 시각) + 리마인더 알림(자기전, 필수 미완료 있을 때만) 2종
- **정렬**: 같은 시각/슬롯 안에서 사용자가 순서(`sort_order`) 직접 변경 가능
- **LLM 안내 문구**: 사용법 안내 / 횟수 소진 안내 / 오류 화면 3종 카피 초안
- **시간 미지정 루틴**: 시스템이 자동 배정하지 않고 사용자가 4개 슬롯 중 직접 선택
- **설정 화면**: 오늘/캘린더/통계 3개 탭 공통 상단 헤더에서 진입, 단일 리스트형 화면 하나로 구성
- **소급 수정**: 루틴 체크는 과거 날짜 수정 불가 / 일기는 과거 날짜도 수정 가능
- **오프라인 처리**: 배너만 표시, 체크/저장 액션은 허용(로컬 반영 후 자동 동기화)
- **스트릭 리셋 기준**: 자정(00:00) — 슬롯 시간과 무관하게 날짜는 항상 자정 기준
- **반복 규칙 변경**: 과거 기록은 그대로 유지, 새 규칙은 변경 시점부터만 적용

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **소프트 삭제를 쓰는 이유**: 루틴을 지워도 그동안 쌓인 완료 기록(통계)은 살아있어야 스트릭/통계가 안 깨짐. 완전 삭제하면 과거 데이터까지 같이 날아감
- **"시각 또는 슬롯 중 하나만" CHECK를 건 이유**: 둘 다 없거나 둘 다 있으면 "이 루틴을 언제 표시해야 하는가"가 애매해짐. DB 단계에서 아예 막아버리면 나중에 버그로 발견하는 것보다 훨씬 안전함
- **RoutineCompletion을 반복 규칙과 무관하게 저장한 이유**: 나중에 루틴의 반복 주기를 바꿔도 과거 기록을 다시 계산할 필요가 없어짐 (기록은 그냥 날짜+값으로 독립적으로 쌓이기 때문)

- 로드맵 1단계 "환경 세팅"부터 실제 개발 착수 (`project-spec.md` 8-1 참고)

## 2026-07-19 (이어서) — 환경 세팅 실행 + DB 생성 + 로그인 구현

### 오늘 한 일 (한 줄 요약)

문서로만 있던 설계를 실제로 돌아가는 앱으로 만들었습니다. Expo 프로젝트 생성 → Supabase에 진짜 DB 테이블 8개 생성(RLS 포함) → 하단 탭 3개(오늘/캘린더/통계) → 구글 로그인까지, 폰에서 실제로 눌러볼 수 있는 상태까지 왔습니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
|---|---|
| Expo / Expo Go | React Native 앱을 쉽게 만들게 도와주는 도구. Expo Go는 폰에 깔아서 개발 중인 앱을 안드로이드 스튜디오 없이 바로 테스트하게 해주는 앱 |
| SDK 버전 | Expo가 몇 달마다 내는 큰 업데이트 단위. 프로젝트가 쓰는 SDK 버전과 폰에 깔린 Expo Go 앱의 지원 버전이 안 맞으면 "incompatible" 에러가 남 |
| 마이그레이션(migration) | DB 테이블 구조를 바꾸는 SQL을 파일로 남겨두는 방식. `0001`, `0002`처럼 순서대로 쌓아서 "이 순서대로 실행하면 항상 같은 DB 구조가 된다"를 보장함 |
| 트리거(trigger) | "어떤 일이 생기면 자동으로 다른 일을 실행해라"는 DB 규칙. 우리는 "구글 로그인 성공 → 프로필+슬롯 4개 자동 생성"을 트리거로 만듦 |
| OAuth | 우리 앱이 직접 비밀번호를 받지 않고, 구글이 "이 사람 맞음"을 대신 확인해주고 우리한테 인증 토큰만 넘겨주는 표준 로그인 방식 |
| 딥링크(deep link) | `dailyloop://...`처럼 앱 전용 주소. 구글 로그인 끝나고 "다시 우리 앱으로 돌아와라"는 신호를 이 주소로 보냄 |
| RLS 실전 적용 | 지난 정리 때 개념만 알았던 RLS를 실제로 8개 테이블에 다 걸었음. 그 결과 로그인 안 하면 데이터를 하나도 못 읽는 게 확인됨 (의도한 대로 작동) |

### 오늘 확정한 결정 요약

- **IDE**: WebStorm → **VS Code로 변경** (이미 쓰고 있던 걸 그대로, 비용 부담 없음 — 실제 코딩은 Claude Code가 터미널에서 하기 때문에 에디터 자체는 큰 영향 없음)
- **RN 시작 방식**: Expo (실기 테스트, Android Studio 설치 안 해도 됨)
- **언어**: TypeScript
- **안드로이드 패키지명**: `com.dailyloop.app`
- **스트릭 이모지 컨셉 2번 변경**: 돌멩이 진화 → (외계인 조우 → 반려) → **자연 요소(물방울→새싹→불씨→구름→나무→무지개→산→세계)**로 최종 확정, 1주 단위로 촘촘히 시작해서 1년까지
- **로그인 우선순위**: 로드맵에 빠져있던 걸 발견해서 "2-1. 로그인 구현" 단계로 추가, 구글부터 먼저 (카카오는 절차가 더 복잡해서 나중)
- **비회원 모드**: 만들지 않기로 확정 (로컬 저장 로직을 따로 만들어야 해서 공수 대비 효과 낮음, 지금처럼 소셜 로그인 버튼 하나로 마찰 최소화하는 쪽 유지)

### 겪었던 문제들과 해결 과정 (이것도 배울 점)

- **문제 1 — Expo Go SDK 버전 불일치**: 새로 만든 프로젝트가 최신 SDK(57)를 썼는데, 폰의 Expo Go 앱이 아직 그 버전을 지원 안 해서 에러. → SDK를 하나 낮췄더니(56) 이번엔 **Expo Go 자체의 버그**(56.0.1이 SDK 56 프로젝트를 잘못 거부하는 알려진 버그)에 걸림 → 결국 확실히 안정적인 SDK 54로 낮춰서 해결. **배운 점**: 에러 메시지를 그대로 검색해보면 "나만 겪는 문제"가 아닌 경우가 많음
- **문제 2 — 템플릿 파일과 SDK 버전 불일치**: SDK 버전만 낮추고 코드 파일은 그대로 뒀더니 다른 에러가 남 (그 코드가 최신 SDK 문법으로 쓰여 있어서). → 낮춘 SDK 버전에 맞는 정품 템플릿 파일을 다시 받아서 통째로 교체
- **문제 3 — 구글 로그인 "provider is not enabled"**: 앱 코드는 문제없었는데, Supabase 대시보드에서 Google 로그인 기능을 켜고 저장하는 걸 안 해서 난 에러. **배운 점**: 에러 메시지의 `message`/`error_description` 부분이 원인을 정확히 알려주니, 에러가 나면 전체 메시지를 다 확인하는 습관이 중요함

## 2026-07-20 — 오늘 탭 완성 + 루틴 CRUD + 모음집/즐겨찾기 + 삭제 정책 정리 + GitHub 연결

### 오늘 한 일 (한 줄 요약)

로드맵 3단계(오늘 탭)와 4단계(루틴 추가/수정 폼)를 완성하고, 원래 계획엔 없던 걸 대화하면서 여러 개 추가했습니다 — 지금 시간 강조 테두리, 공휴일 자동 인식, 자주 쓰는 루틴 묶음(모음집)/즐겨찾기, 스와이프 삭제, 삭제 정책 정리(오늘만 빼기 vs 완전 삭제)까지. 마지막엔 프로젝트를 비공개 GitHub 저장소에 연결하고, 매일 작업 마무리를 자동화하는 "작업끝" 커맨드도 만들었습니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
|---|---|
| Row Level Security(RLS) 실전 확인 | 앱 코드에 있는 `anon key`는 원래 공개돼도 되는 키(숨긴다고 안전해지는 게 아님). 진짜 보안은 DB가 "로그인한 본인 데이터만" 걸러주는 RLS가 담당 — 그래서 키가 유출돼도 남의 데이터는 못 봄 |
| 제스처(스와이프) 라이브러리 | `react-native-gesture-handler` — 화면을 손가락으로 밀었을 때(스와이프) 반응하는 UI를 만들게 해주는 도구. 앱 전체를 `GestureHandlerRootView`로 한 번 감싸야 동작함 |
| 딥링크의 IP 주소 버그 | 폰 테스트용 앱(Expo Go)이 만드는 주소가 `exp://192.168.x.x:포트`처럼 IP 형태인데, 로그인 서버(Supabase Auth)가 IP 형태 주소로의 복귀를 무조건 막는 알려진 버그가 있었음. 터널 모드(`--tunnel`)로 IP 대신 도메인 이름 주소를 쓰게 해서 우회 |
| 대체공휴일 | 원래 공휴일이 토요일/일요일과 겹치면, 그다음 첫 평일을 대신 쉬게 해주는 제도. 모든 공휴일에 적용되는 게 아니라 종류별로 다름(예: 현충일은 대체공휴일 대상이 아님) |
| 소프트 삭제 vs "특정 날짜만 제외" | 완전 삭제(`deleted_at`)는 반복 전체가 사라지는 것, "오늘만 빼기"는 반복 규칙은 그대로 두고 특정 날짜 하나만 예외 테이블(`routine_skip_dates`)에 기록해서 그날만 안 보이게 하는 것 — 서로 다른 테이블/다른 목적 |
| 확인창(Alert) | 되돌리기 어려운 동작(전체 삭제 등) 전에 "정말 할까요?"를 팝업으로 한 번 더 물어보는 것. React Native의 `Alert.alert()`로 구현 |
| 커스텀 슬래시 커맨드 | `.claude/commands/이름.md` 파일을 만들면 `/이름`으로 실행되는 나만의 반복 작업 스크립트가 됨. 오늘 만든 "작업끝"이 그 예시 |

### 오늘 확정한 결정 요약

- **오늘 탭**: 시각순+슬롯순 정렬, 체크/트래킹 완료 입력, 완료율은 이번엔 범위 밖(5단계로 미룸)
- **루틴 추가/수정 폼**: 카테고리·영상연결·알림 필드는 이번엔 제외(해당 기능 자체가 없어서), 모달 화면으로 구현
- **시간 저장 방식 변경**: `scheduled_time`(시각 하나) → `scheduled_time_start`/`scheduled_time_end`(범위)로 스키마 변경. 슬롯 배정 루틴은 강조 대상 아님, 정확한 시각 루틴만 지금 시각이 범위 안이면 테두리 강조(체크해도 유지)
- **공휴일**: `holidays` 테이블 신규, 2026~2027년 시드(노동절·제헌절이 2026년부터 새로 법정공휴일 지정된 것까지 반영). 루틴별 `skip_holidays` 토글로 공휴일엔 반복 무시하고 제외 가능
- **모음집(프리셋)**: 반복 규칙·공휴일 제외는 묶음 전체에 하나로 설정, 개별 항목은 제목/타입/시간/필수만 따로. "적용"하면 항목들이 실제 루틴으로 복사 생성됨
- **즐겨찾기**: 반복 규칙 없는 개별 루틴 템플릿. 루틴 추가 폼에서 별 토글 켜고 저장하면 즐겨찾기에도 같이 저장됨. 즐겨찾기 목록에서 "바로 추가"(즉시 생성)/"수정해서 추가"(폼에 채워넣고 마저 입력) 선택 가능
- **삭제 정책 최종 확정**: 오늘 탭 스와이프 = "오늘만 빼기"(반복 유지), 수정 화면 "루틴삭제" = 반복 전체 완전 삭제(확인창 포함). 둘 다 완료 기록은 안 건드림, 즐겨찾기와도 연동 안 함(그대로 유지)
- **GitHub**: 비공개 저장소로 연결, 로컬 브랜치 `master`→`main`으로 변경

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **시각을 "범위"로 바꾼 이유**: "지금 이 시간대예요" 강조 기능을 만들려면 시작~끝이 있어야 판단 가능. 점 하나(시각)만으론 "언제까지"를 알 수 없었음
- **공휴일 데이터를 API 대신 DB에 직접 넣은 이유**: 외부 API 키 발급·네트워크 의존 없이 오프라인에서도 동작하게 하려고. 대신 1년에 한 번 정도는 직접 갱신해야 함(트레이드오프)
- **"오늘만 빼기"와 "완전 삭제"를 분리한 이유**: 처음엔 하나로 합쳐놨다가, 실제로 써보니 "오늘 하루 쉬는 것"과 "이 루틴 자체를 그만두는 것"은 완전히 다른 상황이라 헷갈렸음. 그래서 예외 날짜만 기록하는 별도 테이블(`routine_skip_dates`)을 새로 만들어 분리함 — 실제 사용해보면서 설계를 고친 좋은 예
- **루틴-즐겨찾기를 서로 연결 안 시킨 이유**: 연결하려면 추가 데이터가 필요한데, 실제로 필요한 상황(루틴 지울 때 즐겨찾기도 같이 지워야 하는 경우)이 없다고 판단해서 단순하게 유지

## 2026-07-21 — 재미 요소(5단계) + 정규식 파싱(6단계) + LLM 무료 한도 정책 확정

### 오늘 한 일 (한 줄 요약)

로드맵 5단계 "재미 요소"(필수 형광펜, 스트릭 이모지, 홈 요약)와 6단계 "정규식 파싱"을 코드로 완성했습니다. 그 외에 자바 개발 환경(JDK) 관련 잡담, LLM 무료 호출 한도를 어떻게 줄지에 대한 정책 논의, Anthropic API 키 발급 시도까지 했습니다(결제 페이지 오류로 발급은 다음으로 미룸).

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
|---|---|
| 스트릭(streak) 계산 | "이 루틴을 오늘 기준으로 며칠 연속 성공했나"를 세는 로직. 오늘부터 하루씩 거슬러 올라가면서, 그 루틴이 원래 하기로 되어있던 날(반복 규칙에 맞는 날)인데 완료 기록이 없으면 거기서 멈춤. 반복 규칙상 원래 안 하는 날(예: 평일만 반복이면 주말)이나 사용자가 "오늘 삭제"로 뺀 날, 공휴일 제외 설정된 날은 "쉬는 날"로 보고 건너뛰어서 스트릭이 안 끊기게 처리함 |
| 배치(batch) 조회 | 루틴이 여러 개일 때 하나씩 DB에 물어보면(N번 요청) 느려지므로, 필요한 데이터(완료기록·건너뛴날짜·공휴일)를 한 번의 요청으로 전부 가져온 다음 메모리에서 나눠 쓰는 방식 |
| 정규식(regex) 파서 | 사용자가 "매일 아침 7시에 물 8잔 마시기"처럼 자연어로 입력했을 때, AI를 부르지 않고도 미리 정해둔 패턴(예: "매일"→daily, "N시"→시각)으로 규칙 기반으로 먼저 해석해보는 로직. 실제 AI 모델 호출 전에 값싸게 처리하는 1차 필터 |
| 하이브리드 파싱 구조 | 정규식으로 먼저 시도하고, 정규식이 아무것도 못 잡아낸 애매한 문장만 그 다음 단계에서 LLM(AI)에 넘기는 방식. AI 호출은 비용이 드니 꼭 필요한 경우에만 쓰기 위한 절충안 |
| 가입 순번 기반 평생 한도 | "이번 달 몇 회" 같은 매달 초기화되는 방식이 아니라, 계정을 만든 시점에 "너는 평생 N회"라고 딱 정해서 주는 방식. 몇 번째로 가입한 계정이냐에 따라 지급량이 다름(선착순 개념) |

### 오늘 확정한 결정 요약

- **필수 형광펜**: 필수 루틴 제목 뒤에 코랄색 반투명 밴드를 살짝 기울여서(-1.5도) 배경으로 깔아 강조. 기존 " · 필수" 텍스트는 제거
- **스트릭 이모지**: `streak_emoji_configs` DB 테이블(이미 만들어둔 8단계 자연 요소 이모지)을 그대로 불러와서 사용. 7일 미만이면 이모지 표시 안 함. "오늘 삭제"한 날/공휴일 제외된 날은 스트릭 카운트에서 쉬는 날로 취급(끊기지 않음)
- **홈 요약**: 리스트 하단에 "오늘 완료 N/M (%)" + "최고 기록 [이모지] N일" 요약바 추가
- **정규식 파싱**: `lib/parse-routine-input.ts`로 반복/시간/필수/트래킹 4가지를 문장에서 추출하는 함수 완성. 아직 이걸 부르는 입력 화면(배너)은 없고, 로직만 먼저 만듦(7단계에서 화면과 함께 연결 예정)
- **LLM 무료 호출 한도 정책 변경**: "계정당 총 10회" → "가입 순번 기반 평생 한도"로 재확정. 최초 가입자 1~10,000번째는 가입 시 10회, 10,001번째부터는 5회 지급(월 단위 초기화 아님). 다 쓰면 "요금제 안내"(아직 요금제 자체가 없어서 "출시 예정" 성격 문구) 노출
- **위챗식 전면 커스터마이징 기능은 보류**: 앱 안에서 위치/크기 자유 배치하는 기능은 지금 단계에선 과한 기능으로 판단해서 안 하기로 함. 대신 "잠금화면/홈 화면에 오늘 할 일 위젯 보여주기"는 나중에(2차 이후) 검토하는 걸로 문서에만 메모해둠 — 안드로이드는 네이티브(Kotlin) 코드가 따로 필요하고, iOS 잠금화면 위젯은 Swift+Mac이 필수라 지금 장비(Windows)로는 개발 자체가 불가능하다는 점도 같이 기록

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **스트릭 계산에서 "오늘 삭제"한 날을 쉬는 날로 처리한 이유**: 도메인 문서에 원래 "반복 규칙상 쉬는 날은 스트릭에서 제외"라고 정해져 있었는데, "오늘 삭제"도 성격이 비슷하다고 판단해서(사용자가 의도적으로 그날만 안 하기로 선택한 것) 같은 방식으로 확장 적용함
- **월 단위 무료 한도 대신 "가입 순번 기반 평생 한도"로 바꾼 이유**: 처음엔 "매달 N회"를 얘기했었는데, 나중에 사용자가 늘어날 걸 대비해서 "먼저 가입한 사람에게 더 많이 준다"는 선착순 개념으로 바꾸는 게 낫다고 판단. 이렇게 하면 초기 사용자 대우도 해주고, 나중에 사용자가 많아져도 전체 비용이 무한정 커지지 않음(신규 가입자 지급량을 5회로 낮춰서 통제)
- **위젯 기능을 문서에만 적어두고 지금 안 만들기로 한 이유**: 새 기술 스택(네이티브 코드)을 통째로 배워야 하는 규모의 작업이라, 1인 개발 하루 2시간 페이스에 안 맞음. 특히 iOS 쪽은 Mac이 없으면 아예 시작도 못 하는 물리적 제약이 있어서 지금은 문서에 아이디어만 남겨두기로 함

- **영상 데이터 수집 방식**: 유튜브 검색 API(키 발급 필요) 대신, 직접 고른 영상 URL + oEmbed(키 불필요)로 메타데이터만 자동으로 가져오는 방식으로 결정. 사용자가 카테고리별 URL을 나중에 주면 그때 DB에 채워 넣기로 함
- **영상 목록 진입 경로**: 루틴 폼의 "영상 연결" 바텀시트뿐 아니라, 오늘 탭 헤더에도 "🎬 영상" 버튼을 놓아서 독립적으로 둘러볼 수 있게 함(버튼이 많아지면 나중에 위치 재검토 예정)
- **유튜브 임베드 방식**: `react-native-webview`로 앱 안에서 직접 재생(외부 유튜브 앱/브라우저로 안 내보냄) — 기획서의 "유튜브 임베드"라는 표현을 그대로 구현

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **API 키 두 개(Anthropic, YouTube Data API)를 굳이 안 쓰기로 한 이유**: 이미 Anthropic 키 발급이 결제 페이지 오류로 막혀있는 상황이라, 지금 당장 또 다른 키 발급 절차를 추가하면 진행이 더 늦어짐. 영상 큐레이션은 "소수 카테고리에 엄선된 영상만" 넣는 컨셉이라 자동 검색보다 사람이 직접 고르는 게 오히려 더 맞았고, 마침 oEmbed라는 키 없는 대안이 있어서 그걸 선택함
- **로드맵 순서를 7단계(LLM) 건너뛰고 8~11단계부터 진행한 이유**: 7단계는 API 키가 있어야만 시작할 수 있는 단계라, 키 없이도 만들 수 있는 다음 단계들을 먼저 끝내서 시간을 낭비하지 않으려고 함. 나중에 키가 생기면 7단계를 그 사이에 끼워 넣으면 됨(로드맵 순서가 절대적인 규칙은 아니고, 막힌 걸 억지로 붙잡고 있지 않는 게 더 중요)
- **영상 큐레이션의 콘텐츠(실제 영상)만 비워두고 화면/기능은 먼저 완성한 이유**: "영상이 없으면 준비 중입니다라고 뜬다"는 빈 상태가 이미 기획서에 정해져 있어서, 데이터가 없어도 화면이 이상하게 깨지지 않고 정상적으로 보임. 그래서 URL을 나중에 받아도 화면 코드를 다시 손댈 필요 없이 데이터만 추가하면 끝나는 구조로 미리 만들어둠

| 안드로이드 WebView 레이어 버그 | 안드로이드 7 이상에서 웹뷰 안의 동영상이 검은 화면으로만 보이는 오래된 버그. `androidLayerType="hardware"`라는 설정으로 완화 가능하지만 100% 해결은 아님 |
| 뷰포트(viewport) | 모바일 웹페이지가 "이 화면을 얼마나 크게 보여줄지" 정하는 설정. 이게 빠지면 웹뷰가 PC 화면 기준 크기로 그렸다가 억지로 축소해서 보여주는데, 이때 눈에 보이는 위치랑 실제 터치 되는 위치가 어긋나는 문제가 생김 |
| 탭하면 키보드 닫기 (`TouchableWithoutFeedback` + `Keyboard.dismiss`) | 입력창 바깥을 탭했을 때 키보드를 내려주는 리액트 네이티브의 표준 패턴 |

| 소프트 삭제를 이용한 안전한 빈 상태 테스트 | 실제 데이터를 완전히 지우지 않고 `deleted_at`만 채워서 "일시적으로 안 보이게" 만든 다음, 확인 끝나면 다시 `null`로 되돌리는 방법. 진짜 삭제(`delete`)와 달리 되돌릴 수 있어서 테스트용으로 안전함 |

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
|---|---|
| 로컬 알림 트리거 종류(DAILY/DATE) | `expo-notifications`가 지원하는 예약 방식. DAILY는 "매일 이 시각에" 반복 예약(슬롯 알림용), DATE는 "이 특정 날짜·시각에 딱 한 번" 예약(리마인더용) — 성격이 다른 두 알림에 각각 맞는 방식을 씀 |
| "앱을 안 열어도 안 놓치는" 리마인더 설계 | 로컬 알림은 폰 안에서만 판단하기 때문에, 앱을 안 열면 "오늘 다 했는지" 알 방법이 없음. 그래서 앱을 열 때마다(또는 체크할 때마다) "다음 발송 시점"을 미리 계산해서 다시 예약해두는 방식을 씀 — 마지막으로 예약해둔 게 그대로 남아있어서 그날 앱을 안 열어도 알림은 감 |
| oEmbed | 유튜브 등 콘텐츠 사이트가 제공하는 "이 링크의 제목/썸네일/채널 정보만 간단히 알려주는" 공개 API. API 키가 필요 없어서 앱에서 바로 호출 가능 |
| 안드로이드 App Link(딥링크)와 `@핸들` 문제 | `youtube.com/@채널명` 같은 링크를 앱에서 열면, 안드로이드 유튜브 앱이 이 형식을 못 알아듣고 그냥 홈 화면으로 떨어지는 경우가 있음(앱 버전에 따른 알려진 버그). 대신 옛날부터 있던 `youtube.com/channel/UC...` 형식(고유 채널ID)은 확실하게 인식해서, 영상 페이지 HTML 안에 숨어있는 채널ID를 직접 찾아 그 형식으로 저장하도록 바꿈 |
| FK `ON DELETE SET NULL` | 어떤 행을 참조하고 있는 다른 테이블이 있을 때, 원본을 지우면 그 참조값을 자동으로 `NULL`로 바꿔주는 DB 규칙. 원래는 참조 중인 행이 있으면 삭제 자체를 막는 설정(`NO ACTION`)이었는데, "루틴에 연결된 영상도 삭제는 가능하게 하고 대신 그 루틴의 영상 연결만 사라지게" 바꾸려고 이 설정으로 교체함 |
| ngrok / authtoken | `--tunnel` 모드가 내부적으로 쓰는 터널링 서비스. 예전엔 로그인 없이도 쓸 수 있었는데 정책이 바뀌어서 무료 계정 가입 후 발급받는 authtoken을 등록해야만 동작함 |

### 오늘 확정한 결정 요약

- **슬롯 알림**: 4개 슬롯(아침/점심/저녁/자기전) 각각 알림 켜면 그 시작 시각에 매일 반복 알림. 설정 화면(`app/settings.tsx`, 신규)에서 슬롯 시간 수정 + 알림 on/off 가능, 3개 탭 공통 헤더에 ⚙️ 아이콘으로 진입
- **리마인더 알림**: 자기전 슬롯 알림이 켜져 있고 그 시각까지 필수 루틴 중 미완료가 있을 때만 발송. "앱을 열 때마다 다음 발송 시점을 다시 계산해서 예약" 방식으로, 개별 루틴 알림(4-9 설계에 있던 것)은 "시끄러울 것 같다"는 이유로 이번엔 빼기로 함
- **개인 영상 추가**: 카테고리 화면에서 유튜브 링크 붙여넣으면 oEmbed로 제목/채널/썸네일 자동 채워서 저장(본인에게만 보임)
- **영상 구조 변경(신규)**: 관리자 공용 영상을 모든 유저 그리드에 자동으로 섞어 보여주던 방식을 버리고, "추천 영상" 탭에서 골라 "내 그리드에 추가"해야만 보이는 방식으로 변경. DB 구조 변경 없이(이미 있던 `user_id` 컬럼 재사용) 추천 영상을 고르면 내 소유로 복사되는 방식으로 구현
- **영상 삭제**: 개인 영상 삭제 버튼 추가. 루틴에 연결된 영상도 "연결된 루틴 N개, 그래도 삭제할까요?" 확인 후 삭제 가능하게 변경 (루틴 자체와 완료 기록은 그대로 남고 영상 연결만 사라짐)
- **일기 스크롤 키보드 버그 수정**: 입력창이 짧으면 스크롤이 아예 안 먹혀서 `keyboardDismissMode="on-drag"`가 무의미했던 문제 → 안 보이는 여백을 화면 아래에 깔아 항상 스크롤 가능하게 만들고, `onScrollBeginDrag`로 드래그 시작 즉시 키보드를 닫도록 보강

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **리마인더를 "앱 열 때마다 재예약"으로 설계한 이유**: 서버 없이 순수 로컬 알림만으로는 "오늘 다 했는지" 여부를 실시간으로 알 수 없음. 그렇다고 무조건 매일 반복 알림을 보내면 이미 다 했는데도 알림이 가는 문제가 생기고, 반대로 아예 안 보내면 앱을 안 연 날은 리마인더 자체가 없어짐. "마지막으로 확인한 상태를 기준으로 다음 알림을 미리 예약해두고, 확인할 때마다 최신 상태로 다시 맞춘다"는 절충안이 로컬 알림의 근본적 한계 안에서 가장 실용적인 방법이었음
- **채널ID를 HTML에서 직접 추출한 이유**: oEmbed API 응답엔 `@핸들` 형식 채널 주소만 들어있는데, 이게 안드로이드 유튜브 앱에서 안정적으로 안 열림. API 키가 필요한 유튜브 데이터 API를 쓰는 대신, 영상 페이지 HTML 안에 이미 채널ID가 텍스트로 박혀있다는 걸 확인하고 그걸 그대로 긁어와 썼음 — 추가 인증 없이 가장 간단하게 해결되는 방법이었음
- **영상 삭제를 막는 대신 "연결 해제"로 바꾼 이유**: 원래 DB 제약(`NO ACTION`)은 "참조되는 행은 절대 못 지움"이라 사용자 입장에서는 이유도 모른 채 삭제가 안 되는 것처럼 보임. 사용자가 원하는 건 "그 영상은 지우되 루틴 자체나 그동안의 기록은 안 사라지는 것"이었고, 이건 `ON DELETE SET NULL`이 DB 레벨에서 정확히 해주는 일이라 앱 코드에서 따로 "연결 해제 후 삭제" 로직을 만들 필요가 없었음
- **관리자 공용 영상을 "추천→선택" 구조로 바꾼 이유**: 처음엔 공용 영상을 모든 유저 그리드에 자동으로 섞어 보여줬는데, 이러면 유저가 "내가 고른 것"과 "관리자가 넣어준 것"을 구분하기 어렵고 그리드가 원치 않는 콘텐츠로 채워질 수 있음. 유저가 명시적으로 "추가"를 눌러야만 내 그리드에 들어오게 하면 그리드가 항상 내가 의도적으로 담은 것들로만 채워짐

## 2026-08-11 — LLM 연동(로드맵 7단계) 착수 + 개인정보처리방침 준비

### 오늘 한 일 요약

드디어 이 앱의 핵심 기능인 **"자연어로 루틴 만들기(AI 배치)"**를 실제로 붙였습니다. Anthropic API 키를 받아서, 앱에 넣지 않고 **서버(Supabase Edge Function)에만** 안전하게 보관하고, 사용자가 "월수금 저녁에 30분씩 러닝하기" 같은 문장을 넣으면 AI(Claude)가 구조화된 루틴으로 바꿔주는 흐름을 만들었습니다. 비용을 아끼려고 **정규식으로 되는 건 공짜로 처리하고 애매한 것만 AI를 부르는** 하이브리드 구조, **가입 순번 기반 평생 호출 한도(10회/5회)**, **입력 100자 제한**까지 넣어 비용을 위아래로 묶었습니다. 뒷부분에는 출시에 필요한 **개인정보처리방침**을 작성해서 GitHub Pages로 공개 웹페이지까지 띄웠습니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
|---|---|
| API 키를 앱에 넣으면 안 되는 이유 | 앱은 빌드된 파일을 누구나 뜯어볼 수 있어서, 키를 앱 안에 넣으면 남이 훔쳐 내 요금으로 AI를 쓸 수 있음. 그래서 키는 **서버에만** 두고, 앱은 서버에 "대신 물어봐줘"라고 부탁하는 구조로 만듦 |
| Edge Function | Supabase가 제공하는 작은 서버 프로그램. 앱 ↔ Edge Function ↔ Anthropic 순으로 중간에서 키를 쥐고 AI를 대신 호출해줌. 키가 앱에 안 들어가는 핵심 장치 |
| Supabase secret | 서버에서만 읽히는 비밀 금고. 여기에 API 키를 넣으면 코드·git 어디에도 안 남고 Edge Function 실행 때만 꺼내 씀 |
| 하이브리드 파싱 | 문장 해석을 두 가지로: ① 정규식(미리 만든 규칙표, 공짜·즉시) 먼저 시도 → ② 규칙표로 애매하면 그때만 AI 호출(유료). "매일 아침 물 마시기"는 규칙표로 잡히니 AI를 안 부름 |
| 서버에서 강제하는 호출 한도 | "무료 10회"를 앱에서만 세면 앱을 조작해 우회할 수 있음. 그래서 DB 함수(RPC)와 가입 트리거로 **서버가 직접** 횟수를 세고 막음 |
| 개인정보 국외 이전 | 데이터가 미국 서버(Supabase·Anthropic)에 저장·전송되므로, 한국 개인정보보호법상 "어느 나라 어느 회사로 무슨 정보가 가는지"를 방침에 명시해야 함 |
| GitHub Pages | GitHub 저장소에 `index.html`을 넣고 스위치를 켜면 무료로 웹주소를 만들어주는 기능. 개인정보방침을 여기에 올려 스토어가 요구하는 "방침 URL"을 확보 |

### 오늘 확정한 결정 요약

- **모델**: `claude-haiku-4-5` (문장→JSON 구조화엔 소형 모델로 충분, 비용 최적화 — 기획서대로)
- **키 보관**: Supabase 대시보드에서 secret `ANTHROPIC_API_KEY`로 등록 (앱·git·채팅 어디에도 원본 안 남김)
- **호출 한도**: 가입 순번 기반 평생 한도(1~10,000번째=10회, 이후=5회). `users`에 `signup_order`·`llm_call_limit` 컬럼 추가 + 가입 트리거·RPC 2개(`get_llm_quota`/`consume_llm_call`)로 서버 강제 → 마이그레이션 `0012_add_llm_quota.sql`
- **미리보기**: LLM이 만든 초안을 기존 루틴 추가 폼(`routine-form`)을 프리필해서 재사용 (기획 4-8 ③ = 초안→사용자 수정→확정 저장)
- **입력 안내 문구 확정**: 규칙 나열 대신 "예시 1개 + 힌트 1줄" (project-spec 4-13)
- **비용 3중 상한**: 입력 100자(앱 입력창 `maxLength`+서버 거부) · 출력 512토큰 · 1인당 평생 10회
- **인증 필수**: Edge Function은 로그인 유저만 호출(`verify_jwt`), `config.toml`에 못박아 재배포 사고 방지
- **개인정보처리방침**: 운영자명 "Daily Loop 개발팀", 이 앱이 실제 수집·전송하는 것만 정직하게 기재(구글·Supabase·Anthropic 국외이전 포함). 코드 저장소는 비공개 유지, 방침만 별도 **공개 저장소 `daily-loop-privacy`**로 GitHub Pages 호스팅 → https://leeyonghee030.github.io/daily-loop-privacy/

### 왜 이렇게 했는지 (설계 이유)

- **키를 서버에 둔 이유**: 모바일 앱은 번들을 추출당하면 안에 든 문자열이 다 보임. 키가 유출되면 제3자가 우리 요금으로 API를 쓰므로, 키를 아는 건 서버뿐이어야 함. 앱은 "이 문장 파싱해줘"만 부탁하고 실제 호출은 서버가 함
- **하이브리드로 만든 이유**: 사람들이 적는 문장 대부분은 규칙표로 충분히 잡힘. 매번 AI를 부르면 돈이 새고 무료 10회도 금방 소진되니, 공짜로 되는 건 공짜로 처리하고 진짜 애매한 것만 AI를 아껴 씀
- **한도를 서버에서 강제한 이유**: 앱에서만 횟수를 세면 조작·우회가 가능. DB 트리거로 가입 시 한도를 심고, 원자적 RPC로 증가시켜 서버가 최종 판정하게 함
- **"짧은 엉뚱한 글로 토큰 낭비"가 큰 문제가 아닌 이유**: 1회 비용은 시스템 프롬프트(고정)+출력 상한(512)으로 이미 작게 묶여 있고, 엉뚱한 글은 정규식에 안 잡혀 AI로 가면서 그 사람 자신의 10회 중 1회만 까먹음. 즉 호출 횟수 제한이 진짜 방어막이라 별도 로직을 더 안 만들고 단순하게 둠
- **방침을 별도 공개 저장소로 뺀 이유**: 무료 GitHub 계정은 비공개 저장소에 Pages를 못 켬. 코드는 비공개로 지키면서 방침 페이지만 공개해야 하므로, 방침만 담은 작은 공개 저장소를 따로 만들어 호스팅함
