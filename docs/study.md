## 2026-07-19 — 서비스기획 → 유저플로우 → 도메인모델 → ERD

### 오늘 한 일 (한 줄 요약)

와이어프레임을 보면서 빠진 부분들(로그인, 알림, 삭제 정책 등)을 하나씩 결정하고, 그 결정들을 **서비스기획서 → 유저플로우 → 도메인모델 → ERD** 순서로 문서화했습니다. (`docs/project-spec.md`, `docs/user-flow.md`, `docs/domain-model.md`, `docs/erd.md`)

이 4개 문서를 순서대로 만드는 이유: 기획(뭘 만들지) → 흐름(사용자가 어떻게 쓸지) → 개념(어떤 데이터가 있는지) → 실제 DB 설계, 이렇게 점점 구체화되는 순서라서 나중에 코드를 짤 때 왔다갔다 헤매지 않게 하기 위함입니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어                              | 쉬운 설명                                                                                                                                                                                |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 유저플로우 (User Flow)            | 사용자가 화면을 어떤 순서로 넘나드는지 그린 지도. "로그인 → 온보딩 → 홈" 같은 화살표 흐름                                                                                                |
| 도메인모델 (Domain Model)         | 앱 안에 어떤 "것들"(User, Routine, Diary...)이 있고 서로 어떻게 연결되는지 정리한 개념도. DB를 만들기 직전 단계의 설계                                                                   |
| ERD (Entity Relationship Diagram) | 도메인모델을 실제 데이터베이스 테이블로 옮긴 설계도. 테이블·컬럼·타입·연결관계를 그림으로 표현                                                                                           |
| PK (Primary Key)                  | 테이블의 각 행(row)을 구분하는 고유 번호. 예: 루틴마다 다른 `id`                                                                                                                         |
| FK (Foreign Key)                  | 다른 테이블의 PK를 가리키는 연결고리. 예: `routines.slot_id`가 `slots.id`를 가리킴 → "이 루틴은 이 슬롯에 속한다"                                                                        |
| 소프트 삭제 (Soft Delete)         | 실제로 행을 지우지 않고 `deleted_at`(삭제된 시각) 컬럼만 채워서 "삭제됨" 표시. 조회할 때 이 값이 비어있는 것만 보여주면 됨. 완전 삭제보다 안전하고, 나중에 복구나 통계 분석에 쓸 수 있음 |
| UNIQUE 제약                       | 특정 컬럼(조합)이 절대 중복되면 안 된다는 DB 규칙. 예: 한 유저가 "아침" 슬롯을 2개 가질 수 없음                                                                                          |
| Partial Unique Index              | 조건부 UNIQUE. 예: "삭제되지 않은 것들 중에서만" 날짜당 일기 1개 — 소프트 삭제와 "하루 1개" 규칙을 동시에 만족시키기 위해 씀                                                             |
| CHECK 제약                        | 컬럼 값이 특정 조건을 만족해야만 저장 가능하게 강제. 예: 루틴은 "정확한 시각"과 "슬롯" 중 반드시 하나만 있어야 함                                                                        |
| RLS (Row Level Security)          | Supabase가 제공하는 DB 레벨 보안 기능. "내 데이터는 나만 조회/수정 가능"하게 서버가 자동으로 막아줌. 아직 우리 프로젝트엔 미적용 상태 (구현 전 확정 필요 항목으로 남겨둠)                |

### 오늘 확정한 결정 요약

- **인증**: 구글 로그인 + 카카오 로그인 둘 다 지원
- **삭제 정책**: 전부 소프트 삭제
- **슬롯**: 시간 커스텀 가능 + 슬롯별 알림 on/off 토글 추가
- **알림(FCM)**: 블록 알림(슬롯 시각) + 리마인더 알림(자기전, 필수 미완료 있을 때만) 2종
- **정렬**: 같은 시각/슬롯 안에서 사용자가 순서(`sort_order`) 직접 변경 가능
- **LLM 안내 문구**: 사용법 안내 / 횟수 소진 안내 / 오류 화면 3종 카피 초안
- **시간 미지정 루틴**: 시스템이 자동 배정하지 않고 사용자가 4개 슬롯 중 직접 선택
- **설정 화면**: 오늘/캘린더/통계 3개 탭 공통 상단 헤더에서 진입, 단일 리스트형 화면 하나로 구성
- **소급 수정**: 루틴 체크는 과거 날짜 수정 불가 / 일기는 과거 날짜도 수정 가능
- **오프라인 처리**: 배너만 표시, 체크/저장 액션은 허용(로컬 반영 후 자동 동기화)
- **스트릭 리셋 기준**: 자정(00:00) — 슬롯 시간과 무관하게 날짜는 항상 자정 기준
- **반복 규칙 변경**: 과거 기록은 그대로 유지, 새 규칙은 변경 시점부터만 적용

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **소프트 삭제를 쓰는 이유**: 루틴을 지워도 그동안 쌓인 완료 기록(통계)은 살아있어야 스트릭/통계가 안 깨짐. 완전 삭제하면 과거 데이터까지 같이 날아감
- **"시각 또는 슬롯 중 하나만" CHECK를 건 이유**: 둘 다 없거나 둘 다 있으면 "이 루틴을 언제 표시해야 하는가"가 애매해짐. DB 단계에서 아예 막아버리면 나중에 버그로 발견하는 것보다 훨씬 안전함
- **RoutineCompletion을 반복 규칙과 무관하게 저장한 이유**: 나중에 루틴의 반복 주기를 바꿔도 과거 기록을 다시 계산할 필요가 없어짐 (기록은 그냥 날짜+값으로 독립적으로 쌓이기 때문)

- 로드맵 1단계 "환경 세팅"부터 실제 개발 착수 (`project-spec.md` 8-1 참고)

## 2026-07-19 (이어서) — 환경 세팅 실행 + DB 생성 + 로그인 구현

### 오늘 한 일 (한 줄 요약)

문서로만 있던 설계를 실제로 돌아가는 앱으로 만들었습니다. Expo 프로젝트 생성 → Supabase에 진짜 DB 테이블 8개 생성(RLS 포함) → 하단 탭 3개(오늘/캘린더/통계) → 구글 로그인까지, 폰에서 실제로 눌러볼 수 있는 상태까지 왔습니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어                    | 쉬운 설명                                                                                                                                       |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Expo / Expo Go          | React Native 앱을 쉽게 만들게 도와주는 도구. Expo Go는 폰에 깔아서 개발 중인 앱을 안드로이드 스튜디오 없이 바로 테스트하게 해주는 앱            |
| SDK 버전                | Expo가 몇 달마다 내는 큰 업데이트 단위. 프로젝트가 쓰는 SDK 버전과 폰에 깔린 Expo Go 앱의 지원 버전이 안 맞으면 "incompatible" 에러가 남        |
| 마이그레이션(migration) | DB 테이블 구조를 바꾸는 SQL을 파일로 남겨두는 방식. `0001`, `0002`처럼 순서대로 쌓아서 "이 순서대로 실행하면 항상 같은 DB 구조가 된다"를 보장함 |
| 트리거(trigger)         | "어떤 일이 생기면 자동으로 다른 일을 실행해라"는 DB 규칙. 우리는 "구글 로그인 성공 → 프로필+슬롯 4개 자동 생성"을 트리거로 만듦                 |
| OAuth                   | 우리 앱이 직접 비밀번호를 받지 않고, 구글이 "이 사람 맞음"을 대신 확인해주고 우리한테 인증 토큰만 넘겨주는 표준 로그인 방식                     |
| 딥링크(deep link)       | `dailyloop://...`처럼 앱 전용 주소. 구글 로그인 끝나고 "다시 우리 앱으로 돌아와라"는 신호를 이 주소로 보냄                                      |
| RLS 실전 적용           | 지난 정리 때 개념만 알았던 RLS를 실제로 8개 테이블에 다 걸었음. 그 결과 로그인 안 하면 데이터를 하나도 못 읽는 게 확인됨 (의도한 대로 작동)     |

### 오늘 확정한 결정 요약

- **IDE**: WebStorm → **VS Code로 변경** (이미 쓰고 있던 걸 그대로, 비용 부담 없음 — 실제 코딩은 Claude Code가 터미널에서 하기 때문에 에디터 자체는 큰 영향 없음)
- **RN 시작 방식**: Expo (실기 테스트, Android Studio 설치 안 해도 됨)
- **언어**: TypeScript
- **안드로이드 패키지명**: `com.dailyloop.app`
- **스트릭 이모지 컨셉 2번 변경**: 돌멩이 진화 → (외계인 조우 → 반려) → **자연 요소(물방울→새싹→불씨→구름→나무→무지개→산→세계)**로 최종 확정, 1주 단위로 촘촘히 시작해서 1년까지
- **로그인 우선순위**: 로드맵에 빠져있던 걸 발견해서 "2-1. 로그인 구현" 단계로 추가, 구글부터 먼저 (카카오는 절차가 더 복잡해서 나중)
- **비회원 모드**: 만들지 않기로 확정 (로컬 저장 로직을 따로 만들어야 해서 공수 대비 효과 낮음, 지금처럼 소셜 로그인 버튼 하나로 마찰 최소화하는 쪽 유지)

### 겪었던 문제들과 해결 과정 (이것도 배울 점)

- **문제 1 — Expo Go SDK 버전 불일치**: 새로 만든 프로젝트가 최신 SDK(57)를 썼는데, 폰의 Expo Go 앱이 아직 그 버전을 지원 안 해서 에러. → SDK를 하나 낮췄더니(56) 이번엔 **Expo Go 자체의 버그**(56.0.1이 SDK 56 프로젝트를 잘못 거부하는 알려진 버그)에 걸림 → 결국 확실히 안정적인 SDK 54로 낮춰서 해결. **배운 점**: 에러 메시지를 그대로 검색해보면 "나만 겪는 문제"가 아닌 경우가 많음
- **문제 2 — 템플릿 파일과 SDK 버전 불일치**: SDK 버전만 낮추고 코드 파일은 그대로 뒀더니 다른 에러가 남 (그 코드가 최신 SDK 문법으로 쓰여 있어서). → 낮춘 SDK 버전에 맞는 정품 템플릿 파일을 다시 받아서 통째로 교체
- **문제 3 — 구글 로그인 "provider is not enabled"**: 앱 코드는 문제없었는데, Supabase 대시보드에서 Google 로그인 기능을 켜고 저장하는 걸 안 해서 난 에러. **배운 점**: 에러 메시지의 `message`/`error_description` 부분이 원인을 정확히 알려주니, 에러가 나면 전체 메시지를 다 확인하는 습관이 중요함

## 2026-07-20 — 오늘 탭 완성 + 루틴 CRUD + 모음집/즐겨찾기 + 삭제 정책 정리 + GitHub 연결

### 오늘 한 일 (한 줄 요약)

로드맵 3단계(오늘 탭)와 4단계(루틴 추가/수정 폼)를 완성하고, 원래 계획엔 없던 걸 대화하면서 여러 개 추가했습니다 — 지금 시간 강조 테두리, 공휴일 자동 인식, 자주 쓰는 루틴 묶음(모음집)/즐겨찾기, 스와이프 삭제, 삭제 정책 정리(오늘만 빼기 vs 완전 삭제)까지. 마지막엔 프로젝트를 비공개 GitHub 저장소에 연결하고, 매일 작업 마무리를 자동화하는 "작업끝" 커맨드도 만들었습니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어                              | 쉬운 설명                                                                                                                                                                                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Row Level Security(RLS) 실전 확인 | 앱 코드에 있는 `anon key`는 원래 공개돼도 되는 키(숨긴다고 안전해지는 게 아님). 진짜 보안은 DB가 "로그인한 본인 데이터만" 걸러주는 RLS가 담당 — 그래서 키가 유출돼도 남의 데이터는 못 봄                                                   |
| 제스처(스와이프) 라이브러리       | `react-native-gesture-handler` — 화면을 손가락으로 밀었을 때(스와이프) 반응하는 UI를 만들게 해주는 도구. 앱 전체를 `GestureHandlerRootView`로 한 번 감싸야 동작함                                                                          |
| 딥링크의 IP 주소 버그             | 폰 테스트용 앱(Expo Go)이 만드는 주소가 `exp://192.168.x.x:포트`처럼 IP 형태인데, 로그인 서버(Supabase Auth)가 IP 형태 주소로의 복귀를 무조건 막는 알려진 버그가 있었음. 터널 모드(`--tunnel`)로 IP 대신 도메인 이름 주소를 쓰게 해서 우회 |
| 대체공휴일                        | 원래 공휴일이 토요일/일요일과 겹치면, 그다음 첫 평일을 대신 쉬게 해주는 제도. 모든 공휴일에 적용되는 게 아니라 종류별로 다름(예: 현충일은 대체공휴일 대상이 아님)                                                                          |
| 소프트 삭제 vs "특정 날짜만 제외" | 완전 삭제(`deleted_at`)는 반복 전체가 사라지는 것, "오늘만 빼기"는 반복 규칙은 그대로 두고 특정 날짜 하나만 예외 테이블(`routine_skip_dates`)에 기록해서 그날만 안 보이게 하는 것 — 서로 다른 테이블/다른 목적                             |
| 확인창(Alert)                     | 되돌리기 어려운 동작(전체 삭제 등) 전에 "정말 할까요?"를 팝업으로 한 번 더 물어보는 것. React Native의 `Alert.alert()`로 구현                                                                                                              |
| 커스텀 슬래시 커맨드              | `.claude/commands/이름.md` 파일을 만들면 `/이름`으로 실행되는 나만의 반복 작업 스크립트가 됨. 오늘 만든 "작업끝"이 그 예시                                                                                                                 |

### 오늘 확정한 결정 요약

- **오늘 탭**: 시각순+슬롯순 정렬, 체크/트래킹 완료 입력, 완료율은 이번엔 범위 밖(5단계로 미룸)
- **루틴 추가/수정 폼**: 카테고리·영상연결·알림 필드는 이번엔 제외(해당 기능 자체가 없어서), 모달 화면으로 구현
- **시간 저장 방식 변경**: `scheduled_time`(시각 하나) → `scheduled_time_start`/`scheduled_time_end`(범위)로 스키마 변경. 슬롯 배정 루틴은 강조 대상 아님, 정확한 시각 루틴만 지금 시각이 범위 안이면 테두리 강조(체크해도 유지)
- **공휴일**: `holidays` 테이블 신규, 2026~2027년 시드(노동절·제헌절이 2026년부터 새로 법정공휴일 지정된 것까지 반영). 루틴별 `skip_holidays` 토글로 공휴일엔 반복 무시하고 제외 가능
- **모음집(프리셋)**: 반복 규칙·공휴일 제외는 묶음 전체에 하나로 설정, 개별 항목은 제목/타입/시간/필수만 따로. "적용"하면 항목들이 실제 루틴으로 복사 생성됨
- **즐겨찾기**: 반복 규칙 없는 개별 루틴 템플릿. 루틴 추가 폼에서 별 토글 켜고 저장하면 즐겨찾기에도 같이 저장됨. 즐겨찾기 목록에서 "바로 추가"(즉시 생성)/"수정해서 추가"(폼에 채워넣고 마저 입력) 선택 가능
- **삭제 정책 최종 확정**: 오늘 탭 스와이프 = "오늘만 빼기"(반복 유지), 수정 화면 "루틴삭제" = 반복 전체 완전 삭제(확인창 포함). 둘 다 완료 기록은 안 건드림, 즐겨찾기와도 연동 안 함(그대로 유지)
- **GitHub**: 비공개 저장소로 연결, 로컬 브랜치 `master`→`main`으로 변경

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **시각을 "범위"로 바꾼 이유**: "지금 이 시간대예요" 강조 기능을 만들려면 시작~끝이 있어야 판단 가능. 점 하나(시각)만으론 "언제까지"를 알 수 없었음
- **공휴일 데이터를 API 대신 DB에 직접 넣은 이유**: 외부 API 키 발급·네트워크 의존 없이 오프라인에서도 동작하게 하려고. 대신 1년에 한 번 정도는 직접 갱신해야 함(트레이드오프)
- **"오늘만 빼기"와 "완전 삭제"를 분리한 이유**: 처음엔 하나로 합쳐놨다가, 실제로 써보니 "오늘 하루 쉬는 것"과 "이 루틴 자체를 그만두는 것"은 완전히 다른 상황이라 헷갈렸음. 그래서 예외 날짜만 기록하는 별도 테이블(`routine_skip_dates`)을 새로 만들어 분리함 — 실제 사용해보면서 설계를 고친 좋은 예
- **루틴-즐겨찾기를 서로 연결 안 시킨 이유**: 연결하려면 추가 데이터가 필요한데, 실제로 필요한 상황(루틴 지울 때 즐겨찾기도 같이 지워야 하는 경우)이 없다고 판단해서 단순하게 유지

- 또는 대화 중 나온 아이디어(캘린더 월/주 토글, 반복 루틴이 만들어지기 전 날짜엔 안 보이게 하기)부터 먼저 해도 됨 — 다음 세션 시작할 때 뭐부터 할지 사용자에게 확인

## 2026-07-21 — 재미 요소(5단계) + 정규식 파싱(6단계) + LLM 무료 한도 정책 확정

### 오늘 한 일 (한 줄 요약)

로드맵 5단계 "재미 요소"(필수 형광펜, 스트릭 이모지, 홈 요약)와 6단계 "정규식 파싱"을 코드로 완성했습니다. 그 외에 자바 개발 환경(JDK) 관련 잡담, LLM 무료 호출 한도를 어떻게 줄지에 대한 정책 논의, Anthropic API 키 발급 시도까지 했습니다(결제 페이지 오류로 발급은 다음으로 미룸).

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어                     | 쉬운 설명                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 스트릭(streak) 계산      | "이 루틴을 오늘 기준으로 며칠 연속 성공했나"를 세는 로직. 오늘부터 하루씩 거슬러 올라가면서, 그 루틴이 원래 하기로 되어있던 날(반복 규칙에 맞는 날)인데 완료 기록이 없으면 거기서 멈춤. 반복 규칙상 원래 안 하는 날(예: 평일만 반복이면 주말)이나 사용자가 "오늘 삭제"로 뺀 날, 공휴일 제외 설정된 날은 "쉬는 날"로 보고 건너뛰어서 스트릭이 안 끊기게 처리함 |
| 배치(batch) 조회         | 루틴이 여러 개일 때 하나씩 DB에 물어보면(N번 요청) 느려지므로, 필요한 데이터(완료기록·건너뛴날짜·공휴일)를 한 번의 요청으로 전부 가져온 다음 메모리에서 나눠 쓰는 방식                                                                                                                                                                                        |
| 정규식(regex) 파서       | 사용자가 "매일 아침 7시에 물 8잔 마시기"처럼 자연어로 입력했을 때, AI를 부르지 않고도 미리 정해둔 패턴(예: "매일"→daily, "N시"→시각)으로 규칙 기반으로 먼저 해석해보는 로직. 실제 AI 모델 호출 전에 값싸게 처리하는 1차 필터                                                                                                                                  |
| 하이브리드 파싱 구조     | 정규식으로 먼저 시도하고, 정규식이 아무것도 못 잡아낸 애매한 문장만 그 다음 단계에서 LLM(AI)에 넘기는 방식. AI 호출은 비용이 드니 꼭 필요한 경우에만 쓰기 위한 절충안                                                                                                                                                                                         |
| 가입 순번 기반 평생 한도 | "이번 달 몇 회" 같은 매달 초기화되는 방식이 아니라, 계정을 만든 시점에 "너는 평생 N회"라고 딱 정해서 주는 방식. 몇 번째로 가입한 계정이냐에 따라 지급량이 다름(선착순 개념)                                                                                                                                                                                   |

### 오늘 확정한 결정 요약

- **필수 형광펜**: 필수 루틴 제목 뒤에 코랄색 반투명 밴드를 살짝 기울여서(-1.5도) 배경으로 깔아 강조. 기존 " · 필수" 텍스트는 제거
- **스트릭 이모지**: `streak_emoji_configs` DB 테이블(이미 만들어둔 8단계 자연 요소 이모지)을 그대로 불러와서 사용. 7일 미만이면 이모지 표시 안 함. "오늘 삭제"한 날/공휴일 제외된 날은 스트릭 카운트에서 쉬는 날로 취급(끊기지 않음)
- **홈 요약**: 리스트 하단에 "오늘 완료 N/M (%)" + "최고 기록 [이모지] N일" 요약바 추가
- **정규식 파싱**: `lib/parse-routine-input.ts`로 반복/시간/필수/트래킹 4가지를 문장에서 추출하는 함수 완성. 아직 이걸 부르는 입력 화면(배너)은 없고, 로직만 먼저 만듦(7단계에서 화면과 함께 연결 예정)
- **LLM 무료 호출 한도 정책 변경**: "계정당 총 10회" → "가입 순번 기반 평생 한도"로 재확정. 최초 가입자 1~10,000번째는 가입 시 10회, 10,001번째부터는 5회 지급(월 단위 초기화 아님). 다 쓰면 "요금제 안내"(아직 요금제 자체가 없어서 "출시 예정" 성격 문구) 노출
- **위챗식 전면 커스터마이징 기능은 보류**: 앱 안에서 위치/크기 자유 배치하는 기능은 지금 단계에선 과한 기능으로 판단해서 안 하기로 함. 대신 "잠금화면/홈 화면에 오늘 할 일 위젯 보여주기"는 나중에(2차 이후) 검토하는 걸로 문서에만 메모해둠 — 안드로이드는 네이티브(Kotlin) 코드가 따로 필요하고, iOS 잠금화면 위젯은 Swift+Mac이 필수라 지금 장비(Windows)로는 개발 자체가 불가능하다는 점도 같이 기록

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **스트릭 계산에서 "오늘 삭제"한 날을 쉬는 날로 처리한 이유**: 도메인 문서에 원래 "반복 규칙상 쉬는 날은 스트릭에서 제외"라고 정해져 있었는데, "오늘 삭제"도 성격이 비슷하다고 판단해서(사용자가 의도적으로 그날만 안 하기로 선택한 것) 같은 방식으로 확장 적용함
- **월 단위 무료 한도 대신 "가입 순번 기반 평생 한도"로 바꾼 이유**: 처음엔 "매달 N회"를 얘기했었는데, 나중에 사용자가 늘어날 걸 대비해서 "먼저 가입한 사람에게 더 많이 준다"는 선착순 개념으로 바꾸는 게 낫다고 판단. 이렇게 하면 초기 사용자 대우도 해주고, 나중에 사용자가 많아져도 전체 비용이 무한정 커지지 않음(신규 가입자 지급량을 5회로 낮춰서 통제)
- **위젯 기능을 문서에만 적어두고 지금 안 만들기로 한 이유**: 새 기술 스택(네이티브 코드)을 통째로 배워야 하는 규모의 작업이라, 1인 개발 하루 2시간 페이스에 안 맞음. 특히 iOS 쪽은 Mac이 없으면 아예 시작도 못 하는 물리적 제약이 있어서 지금은 문서에 아이디어만 남겨두기로 함

- **영상 데이터 수집 방식**: 유튜브 검색 API(키 발급 필요) 대신, 직접 고른 영상 URL + oEmbed(키 불필요)로 메타데이터만 자동으로 가져오는 방식으로 결정. 사용자가 카테고리별 URL을 나중에 주면 그때 DB에 채워 넣기로 함
- **영상 목록 진입 경로**: 루틴 폼의 "영상 연결" 바텀시트뿐 아니라, 오늘 탭 헤더에도 "🎬 영상" 버튼을 놓아서 독립적으로 둘러볼 수 있게 함(버튼이 많아지면 나중에 위치 재검토 예정)
- **유튜브 임베드 방식**: `react-native-webview`로 앱 안에서 직접 재생(외부 유튜브 앱/브라우저로 안 내보냄) — 기획서의 "유튜브 임베드"라는 표현을 그대로 구현

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **API 키 두 개(Anthropic, YouTube Data API)를 굳이 안 쓰기로 한 이유**: 이미 Anthropic 키 발급이 결제 페이지 오류로 막혀있는 상황이라, 지금 당장 또 다른 키 발급 절차를 추가하면 진행이 더 늦어짐. 영상 큐레이션은 "소수 카테고리에 엄선된 영상만" 넣는 컨셉이라 자동 검색보다 사람이 직접 고르는 게 오히려 더 맞았고, 마침 oEmbed라는 키 없는 대안이 있어서 그걸 선택함
- **로드맵 순서를 7단계(LLM) 건너뛰고 8~11단계부터 진행한 이유**: 7단계는 API 키가 있어야만 시작할 수 있는 단계라, 키 없이도 만들 수 있는 다음 단계들을 먼저 끝내서 시간을 낭비하지 않으려고 함. 나중에 키가 생기면 7단계를 그 사이에 끼워 넣으면 됨(로드맵 순서가 절대적인 규칙은 아니고, 막힌 걸 억지로 붙잡고 있지 않는 게 더 중요)
- **영상 큐레이션의 콘텐츠(실제 영상)만 비워두고 화면/기능은 먼저 완성한 이유**: "영상이 없으면 준비 중입니다라고 뜬다"는 빈 상태가 이미 기획서에 정해져 있어서, 데이터가 없어도 화면이 이상하게 깨지지 않고 정상적으로 보임. 그래서 URL을 나중에 받아도 화면 코드를 다시 손댈 필요 없이 데이터만 추가하면 끝나는 구조로 미리 만들어둠

- **개인 영상 기능을 새 테이블 대신 기존 테이블에 컬럼만 추가하기로 한 이유**: 루틴은 이미 `video_id`로 `videos` 테이블 하나만 참조하고 있음. 개인 영상을 위해 테이블을 하나 더 만들면 루틴 쪽에 참조 컬럼이 하나 더 필요해지고, "어느 테이블에서 찾아야 하는지" 분기 로직도 늘어남. 기존 테이블에 소유자 컬럼 하나만 추가하면 이미 만들어둔 목록/선택/재생 화면을 거의 그대로 재사용할 수 있어서 구조가 훨씬 단순해짐

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어                                       | 쉬운 설명                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 로컬 알림 트리거 종류(DAILY/DATE)          | `expo-notifications`가 지원하는 예약 방식. DAILY는 "매일 이 시각에" 반복 예약(슬롯 알림용), DATE는 "이 특정 날짜·시각에 딱 한 번" 예약(리마인더용) — 성격이 다른 두 알림에 각각 맞는 방식을 씀                                                                                                                                     |

API 키가 필요 없어서 앱에서 바로 호출 가능                                                                                                                                                                                        |

| FK `ON DELETE SET NULL`                    | 어떤 행을 참조하고 있는 다른 테이블이 있을 때, 원본을 지우면 그 참조값을 자동으로 `NULL`로 바꿔주는 DB 규칙. 원래는 참조 중인 행이 있으면 삭제 자체를 막는 설정(`NO ACTION`)이었는데, "루틴에 연결된 영상도 삭제는 가능하게 하고 대신 그 루틴의 영상 연결만 사라지게" 바꾸려고 이 설정으로 교체함                                  |

### 오늘 확정한 결정 요약

- **슬롯 알림**: 4개 슬롯(아침/점심/저녁/자기전) 각각 알림 켜면 그 시작 시각에 매일 반복 알림. 설정 화면(`app/settings.tsx`, 신규)에서 슬롯 시간 수정 + 알림 on/off 가능, 3개 탭 공통 헤더에 ⚙️ 아이콘으로 진입
- **리마인더 알림**: 자기전 슬롯 알림이 켜져 있고 그 시각까지 필수 루틴 중 미완료가 있을 때만 발송. "앱을 열 때마다 다음 발송 시점을 다시 계산해서 예약" 방식으로, 개별 루틴 알림(4-9 설계에 있던 것)은 "시끄러울 것 같다"는 이유로 이번엔 빼기로 함
- **개인 영상 추가**: 카테고리 화면에서 유튜브 링크 붙여넣으면 oEmbed로 제목/채널/썸네일 자동 채워서 저장(본인에게만 보임)
- **영상 구조 변경(신규)**: 관리자 공용 영상을 모든 유저 그리드에 자동으로 섞어 보여주던 방식을 버리고, "추천 영상" 탭에서 골라 "내 그리드에 추가"해야만 보이는 방식으로 변경. DB 구조 변경 없이(이미 있던 `user_id` 컬럼 재사용) 추천 영상을 고르면 내 소유로 복사되는 방식으로 구현
- **영상 삭제**: 개인 영상 삭제 버튼 추가. 루틴에 연결된 영상도 "연결된 루틴 N개, 그래도 삭제할까요?" 확인 후 삭제 가능하게 변경 (루틴 자체와 완료 기록은 그대로 남고 영상 연결만 사라짐)
- **일기 스크롤 키보드 버그 수정**: 입력창이 짧으면 스크롤이 아예 안 먹혀서 `keyboardDismissMode="on-drag"`가 무의미했던 문제 → 안 보이는 여백을 화면 아래에 깔아 항상 스크롤 가능하게 만들고, `onScrollBeginDrag`로 드래그 시작 즉시 키보드를 닫도록 보강

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **리마인더를 "앱 열 때마다 재예약"으로 설계한 이유**: 서버 없이 순수 로컬 알림만으로는 "오늘 다 했는지" 여부를 실시간으로 알 수 없음. 그렇다고 무조건 매일 반복 알림을 보내면 이미 다 했는데도 알림이 가는 문제가 생기고, 반대로 아예 안 보내면 앱을 안 연 날은 리마인더 자체가 없어짐. "마지막으로 확인한 상태를 기준으로 다음 알림을 미리 예약해두고, 확인할 때마다 최신 상태로 다시 맞춘다"는 절충안이 로컬 알림의 근본적 한계 안에서 가장 실용적인 방법이었음
- **채널ID를 HTML에서 직접 추출한 이유**: oEmbed API 응답엔 `@핸들` 형식 채널 주소만 들어있는데, 이게 안드로이드 유튜브 앱에서 안정적으로 안 열림. API 키가 필요한 유튜브 데이터 API를 쓰는 대신, 영상 페이지 HTML 안에 이미 채널ID가 텍스트로 박혀있다는 걸 확인하고 그걸 그대로 긁어와 썼음 — 추가 인증 없이 가장 간단하게 해결되는 방법이었음
- **영상 삭제를 막는 대신 "연결 해제"로 바꾼 이유**: 원래 DB 제약(`NO ACTION`)은 "참조되는 행은 절대 못 지움"이라 사용자 입장에서는 이유도 모른 채 삭제가 안 되는 것처럼 보임. 사용자가 원하는 건 "그 영상은 지우되 루틴 자체나 그동안의 기록은 안 사라지는 것"이었고, 이건 `ON DELETE SET NULL`이 DB 레벨에서 정확히 해주는 일이라 앱 코드에서 따로 "연결 해제 후 삭제" 로직을 만들 필요가 없었음
- **관리자 공용 영상을 "추천→선택" 구조로 바꾼 이유**: 처음엔 공용 영상을 모든 유저 그리드에 자동으로 섞어 보여줬는데, 이러면 유저가 "내가 고른 것"과 "관리자가 넣어준 것"을 구분하기 어렵고 그리드가 원치 않는 콘텐츠로 채워질 수 있음. 유저가 명시적으로 "추가"를 눌러야만 내 그리드에 들어오게 하면 그리드가 항상 내가 의도적으로 담은 것들로만 채워짐

- **하이브리드로 만든 이유**: 사람들이 적는 문장 대부분은 규칙표로 충분히 잡힘. 매번 AI를 부르면 돈이 새고 무료 10회도 금방 소진되니, 공짜로 되는 건 공짜로 처리하고 진짜 애매한 것만 AI를 아껴 씀

- **"짧은 엉뚱한 글로 토큰 낭비"가 큰 문제가 아닌 이유**: 1회 비용은 시스템 프롬프트(고정)+출력 상한(512)으로 이미 작게 묶여 있고, 엉뚱한 글은 정규식에 안 잡혀 AI로 가면서 그 사람 자신의 10회 중 1회만 까먹음. 즉 호출 횟수 제한이 진짜 방어막이라 별도 로직을 더 안 만들고 단순하게 둠
- **방침을 별도 공개 저장소로 뺀 이유**: 무료 GitHub 계정은 비공개 저장소에 Pages를 못 켬. 코드는 비공개로 지키면서 방침 페이지만 공개해야 하므로, 방침만 담은 작은 공개 저장소를 따로 만들어 호스팅함

| 네비게이션 `replace` vs `push`           | `replace`는 지금 화면을 스택에서 지우고 새 화면으로 바꿔치기, `push`는 스택에 새로 쌓기. `replace`를 쓰면 뒤로가기 했을 때 지운 화면을 건너뛰고 그 전 화면으로 가버려서, "말로 루틴 추가" 화면이 뒤로가기 스택에서 통째로 사라지는 버그가 났음                      |

### 오늘 확정한 결정 요약

- **LLM 파서**: 정규식이 신호어 하나만 잡아도 AI를 건너뛰던 하이브리드 로직은 유지하되(비용 통제), 대신 정규식 자체를 훨씬 정교하게 다듬음(반복/시간대/트래킹 키워드 확장, 제목에서 조사·명령형 표현·의도 표현 제거) + 사용자가 직접 AI를 강제로 쓸 수 있는 버튼 추가
- **새 화면/기능 10종 추가**: 오늘 탭 타임라인 뷰(리스트와 전환), 캘린더 주간 뷰(가로 컬럼), 통계 주간/월별 전환 + 카드 숨기기, "내 루틴" 전체보기(필터+드래그 정렬+삭제), 루틴 메모+사진 첨부. **카테고리 선택 UI는 폼에서 완전히 제거**(영상 선택 화면에서도 안 쓰이던 죽은 기능이었음이 확인돼서 삭제하기로 함)
- **타임라인 뷰 설계**: 슬롯형(아침/점심 등) 루틴은 슬롯 전체 범위가 아니라 시작 시각에 작은 블록만 표시(그래야 다른 블록과 안 겹침), 겹치는 시간대는 자동으로 옆으로 나란히 배치
- **드래그 순서 정렬**: 오늘 탭(시간순 자동 정렬이 핵심이라 드래그와 상성이 안 맞음)이 아니라 "내 루틴" 화면에서만 지원, 모든 필터 탭에서 가능

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **하이브리드 분기 로직 자체는 안 바꾸고 정규식만 키운 이유**: 분기를 뒤집어서 대부분 문장을 AI로 보내면 정확도는 오르지만 무료 횟수(10회/5회)가 훨씬 빨리 소진됨. 대신 정규식 커버리지를 넓히는 쪽을 택해서, 비용은 그대로 통제하면서 체감 정확도만 끌어올림
- **타임라인 슬롯 블록을 실제 설정 시각에 고정한 이유**: "아침은 무조건 5시"처럼 하드코딩하면 설정 화면에서 슬롯 시간을 바꿔도 타임라인에 반영이 안 돼서 오히려 헷갈림. 실제 설정값을 그대로 쓰는 게 일관성 있음
- **드래그 정렬을 오늘 탭이 아니라 내 루틴 화면에만 넣은 이유**: 오늘 탭은 시간순으로 자동 정렬되는 게 핵심 기능인데, 여기서 자유 드래그를 허용하면 새로고침마다 순서가 시간순으로 다시 흐트러져서 사용자가 방금 바꾼 순서가 없어진 것처럼 보임. 시간과 무관하게 목록을 관리하는 화면(내 루틴)에만 넣는 게 충돌이 없음
- **사진 업로드 실패해도 나머지 저장은 진행하게 바꾼 이유**: 처음엔 사진 업로드 실패 시 저장 전체를 막았는데, 그러면 제목·카테고리 등 다른 변경사항까지 전부 날아감. 사진은 부가 기능이라 실패해도 별도로 안내만 하고 나머지 저장은 그대로 진행하는 게 사용자 손실이 적음

## 2026-08-24 — 폰 실기 QA 라운드 + 루틴 복구(휴지통) 기능 신설

### 오늘 한 일 요약

전날(2026-08-23) 만든 기능 10종을 폰으로 하나씩 눌러보면서 나온 버그를 계속 고쳤습니다. 특히 "내 루틴" 드래그 정렬은 두 번이나 직접 구현을 시도했는데도 계속 실패해서, 결국 전용 라이브러리로 교체하고 나서야 해결됐습니다. 그 과정에서 "삭제해도 2주 안엔 되돌릴 수 있으면 좋겠다"는 요청이 나와서, 루틴뿐 아니라 모음집까지 통째로 복구할 수 있는 "루틴 복구" 화면을 새로 만들었습니다. 마지막엔 구글 로그인 터널 연결이 안 되는 문제를 진단해서 원인(네트워크가 ngrok 터널 트래픽을 막고 있었음)까지 찾아냈습니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
| --- | --- |
| 라이브러리 버전 호환성 문제 | 어떤 기능(예: 드래그 정렬)을 도와주는 외부 라이브러리가, 우리 프로젝트가 쓰는 다른 핵심 라이브러리(Reanimated)의 최신 버전과 안 맞아서 생기는 문제. 겉으론 "그냥 안 됨"으로만 보여서 원인 찾기가 어려움 — 오래된 라이브러리를 최신 버전과 호환되는 걸로 바꿔서 해결함 |
| 스크롤뷰와 자식 컴포넌트의 터치 경합 | 리스트(스크롤 가능한 화면) 안에 드래그 가능한 항목을 넣으면, 손가락을 움직였을 때 "이건 화면 스크롤이다"와 "이건 항목 드래그다" 둘 중 뭘 우선할지 시스템이 헷갈려서 계속 뺏고 뺏기는 현상. 드래그 중엔 스크롤 자체를 꺼버리는 식으로 해결 시도했지만, 결국 이 문제까지 다 처리해둔 전용 라이브러리로 바꾸는 게 가장 확실했음 |
| 하드 삭제 vs 소프트 삭제가 섞였을 때 생기는 문제 | 모음집은 하드 삭제(즉시 완전 삭제), 그 모음집으로 만든 루틴은 소프트 삭제(표시만)로 서로 다르게 처리하고 있었는데, 모음집을 지우는 순간 DB의 "연결 규칙"(외래키)이 자동으로 루틴의 "어느 모음집 소속인지" 정보를 지워버려서, 나중에 "모음집째로 복구"가 불가능해지는 문제가 있었음. 모음집도 소프트 삭제로 바꿔서 연결 정보 자체가 안 끊기게 고침 |
| 로컬 저장소(AsyncStorage)로 "하루에 한 번만" 구현하기 | 서버 없이 이 폰 안에만 "오늘 이 안내문구를 봤다"는 날짜를 저장해두고, 앱을 다시 열 때 그 날짜와 오늘 날짜를 비교해서 같으면 안 띄우는 방식. 서버 스케줄러 없이도 "하루 한 번" 같은 동작을 구현할 수 있음 |
| TLS 핸드셰이크 실패 | 두 컴퓨터가 암호화 연결을 맺기 전에 "어떤 암호화 방식을 쓸지" 협상하는 과정. 이 협상 자체가 실패하면 연결 시도는 되는데(TCP는 연결됨) 실제 데이터는 못 주고받음 — 방화벽/백신이 이 협상 과정을 방해할 때 흔히 생김 |

### 오늘 확정한 결정 요약

- **드래그 정렬 라이브러리 교체**: `react-native-draggable-flatlist`(오래된 라이브러리, Reanimated 4와 호환 안 돼서 "내 루틴" 화면 자체가 안 뜨는 원인이었음) → `react-native-reorderable-list`로 교체. 직접 만든 구현(RN 코어 PanResponder)은 두 번 시도했지만 스크롤뷰와의 터치 경합을 완전히 못 잡아서 최종적으로 라이브러리로 결정
- **"내 루틴" 화면 구조 변경**: "반복주기" / "모음집" 두 개의 탭으로 분리(동시에 같이 필터링하면 헷갈려서). 모음집 탭은 처음엔 비어있고, 특정 모음집을 골라야만 그 루틴들이 보임
- **루틴 일시정지 기능 추가**: `routines.is_paused` 컬럼 신설(마이그레이션 `0015`) — 삭제와 달리 오늘 탭·캘린더·통계에서만 숨기고 완전히 지우지는 않음. 모음집 화면에서 "전체 비활성화/활성화"로 일괄 적용 가능
- **모음집-루틴 연결 추적**: `routines.preset_id` 컬럼 신설(마이그레이션 `0015`) — 어떤 모음집에서 만들어진 루틴인지 기록. 기존에 이미 만들어져 있던 루틴은 추적 정보가 없어서 "미분류"로 남음(문제없음, 앞으로 만드는 것부터 적용)
- **모음집도 소프트 삭제로 전환**: `routine_presets.deleted_at` 컬럼 신설(마이그레이션 `0016`) — 모음집을 지워도 실제로는 안 지우고 표시만 해서, 나중에 그 모음집이 만든 루틴들과의 연결이 안 끊기게 함
- **"루틴 복구" 화면 신설**: 삭제한 루틴/모음집은 바로 없어지지 않고 **2주** 동안 복구 가능(원래 2개월로 만들었다가 테스트 편의상 2주로 줄임). 모음집을 통째로 지운 경우엔 그 모음집으로 만들어진 루틴들이 개별 항목이 아니라 "모음집 카드" 하나로 묶여서 보이고, "모음집 복구" 버튼 하나로 전부 되살아남. "선택 삭제" 모드로 2주를 기다리지 않고 즉시 완전 삭제(되돌릴 수 없음)도 가능
- **자동 정리(purge)**: 앱을 열 때마다 하루 한 번만 조용히 확인해서, 삭제된 지 2주 지난 루틴/모음집을 완전히 지움. 서버 스케줄러(cron) 없이 클라이언트에서 처리
- **오늘 탭 헤더 정리**: "+ 루틴 추가" 버튼을 "오늘" 글자와 같은 줄 오른쪽 끝으로 이동, 이메일 표시 제거(→ 설정 화면으로 이동), 상단 여백 축소. "내 루틴" 화면의 "+ 루틴 추가"는 "♻️ 루틴 복구" 버튼으로 교체
- **로그아웃 위치 이동**: 오늘 탭 하단 → 설정(⚙️) 화면의 "계정" 섹션으로
- **말로 루틴 추가 네비게이션 버그 수정**: 미리보기에서 뒤로가기하면 오늘 탭까지 건너뛰던 문제, 저장 완료 후에도 입력 화면으로 돌아가던 문제 둘 다 수정
- **타임라인 같은 슬롯 겹침 수정 + 안내 배너**: 같은 슬롯(아침 등)에 루틴이 여러 개면 세로로 쌓이게 하고, 그 순서를 바꾸려면 "내 루틴"에서 드래그해야 한다는 안내 배너를 하루 한 번(또는 "다시 안 보기" 선택 시 영구히) 노출

### 왜 이렇게 했는지 (설계 이유 몇 가지)

- **커스텀 드래그 구현을 포기하고 라이브러리로 바꾼 이유**: 첫 시도는 "손을 놓을 때 흔들리기만 하고 안 움직이는" 증상이 있었는데, 원인이 스크롤뷰가 제스처를 도중에 가로채가는 것으로 확인되어 대응 코드를 추가했지만 두 번째 시도에서도 같은 증상이 재현됨. 이런 "리스트 스크롤과 항목 드래그의 충돌"은 이미 여러 라이브러리가 오랫동안 다뤄온 어려운 문제라, 직접 다 잡으려 하기보다 이미 검증된 라이브러리를 쓰는 게 더 빠르고 안정적이라고 판단함
- **모음집을 소프트 삭제로 바꾼 이유**: 하드 삭제(즉시 완전 삭제)를 쓰면 DB의 외래키 규칙(연결된 루틴이 있어도 삭제 허용, 대신 연결만 끊기) 때문에 삭제 순간 루틴의 "어느 모음집 소속인지" 정보가 사라져버려서, 나중에 "모음집째로 되돌리기"가 원천적으로 불가능해짐. 소프트 삭제로 바꾸면 모음집 행 자체가 실제로 남아있어서 연결이 유지되고, 복구 기능을 만들 수 있게 됨
- **자동 정리를 서버 스케줄러 대신 클라이언트에서 처리한 이유**: 이 앱은 사용자가 하루에 한 번 이상 여는 개인용 앱이라, 서버에 크론(정해진 시간마다 자동 실행)을 따로 두지 않아도 "앱 열 때 확인"만으로 충분함. 별도 서버 인프라 없이 간단하게 구현 가능
- **2개월 → 2주로 줄인 이유**: 2개월은 실제로 그 기간이 지나야 동작을 확인할 수 있어서 테스트 자체가 불가능했음. 2주도 여전히 길지만, "복구 가능 기간을 넉넉히 준다"는 취지는 유지하면서 실사용 관점에서도 합리적인 기간으로 조정함
- **선택 삭제(즉시 완전 삭제)를 별도로 만든 이유**: 2주 보관은 실수 방지용 안전장치인데, 사용자가 확실히 안 쓸 걸 알고 있는 항목까지 굳이 2주씩 붙잡아둘 필요는 없어서, 원하면 바로 완전히 지울 수 있는 선택지를 같이 제공함(대신 되돌릴 수 없다고 명확히 경고)

| 소프트 삭제 vs 완전삭제(하드 삭제) | 소프트 삭제는 "삭제됨" 표시만 해두고 실제 데이터는 DB에 그대로 두는 것(복구 가능). 완전삭제는 데이터베이스에서 그 줄 자체를 영영 지우는 것(복구 불가능). 오늘 이 둘을 확실히 구분해서, 루틴은 무조건 소프트 삭제만 하기로 정함 |
| CASCADE 삭제(연쇄 삭제) | 데이터베이스에서 "부모"가 지워지면 거기 딸린 "자식" 데이터도 자동으로 같이 지워지게 미리 설정해두는 규칙. 루틴을 완전삭제하면 그 루틴의 완료 기록도 이 규칙 때문에 자동으로 같이 사라졌던 것이 이번에 발견한 문제의 핵심 원인 |
| UTC와 시간대(타임존) | 컴퓨터/서버는 전 세계 공통 기준 시각(UTC)으로 시간을 저장하고, 화면에 보여줄 때만 사용자의 지역 시간(한국은 UTC+9)으로 바꿔서 보여줌. 이 변환을 안 해주고 그냥 앞 10글자만 잘라서 날짜를 비교하면, 자정 근처(밤 12시~아침 9시)에 한 일이 하루 어긋나 보이는 버그가 생김(오늘 겪은 "27일 데이터가 왜 생기지" 버그의 원인) |
| Stale-While-Revalidate(오래된 데이터 먼저 보여주고 나중에 갱신) | 새 데이터를 받아오는 동안 화면을 비우거나 로딩 표시를 띄우는 대신, 일단 예전에 받아둔(약간 오래된) 데이터를 그대로 보여주고, 새 데이터가 도착하면 조용히 바꿔치기하는 방식. 로딩이 안 보이는 것처럼 느껴지게 하는 흔한 기법 |
| 가상 DOM 재조정과 리렌더 타이밍 | 화면에 뭔가를 스크롤시키는 명령은 "실제로 그 내용이 화면에 그려진 뒤"에 내려야 제대로 작동함. 데이터를 받자마자(아직 화면에 반영되기 전에) 스크롤 명령을 내리면 조용히 무시될 수 있어서, "다음 프레임까지 기다렸다가" 실행하는 기법(`requestAnimationFrame`)을 씀 |
| 함수 호이스팅(hoisting) | 자바스크립트에서 `function 이름() {...}` 형태로 만든 함수는, 코드에서 그 함수를 실제로 쓰는 부분이 함수 정의보다 위에 있어도 문제없이 미리 쓸 수 있음(엔진이 미리 끌어올려 등록해두기 때문) |

### 확정한 결정

- **새 루틴 시간 타입 "시각 체크" 추가**: "정확한 시각(범위)" / "시각 체크(순간)" / "슬롯" 3가지 중 선택. 루틴 폼·모음집 항목·즐겨찾기 셋 다 동일하게 적용. 내부적으로는 시작=끝=같은 시각으로 저장하고 `is_instant` 플래그를 따로 둠
- **시간 선택기 15분 단위로 변경**(`minuteInterval={15}`), **끝 시각이 시작보다 같거나 빠르면 무시**(단, 자정에 끝나는 루틴을 위해 00:00만 예외 허용)
- **루틴은 앞으로 절대 완전삭제(하드 삭제)하지 않기로 확정**. "루틴 복구" 화면의 "선택 삭제"는 이제 모음집(템플릿, 완료기록이 안 달려있어 안전)만 완전삭제하고, 루틴은 `archived_at`이라는 새 컬럼으로 "복구 목록에서만 숨기기" 처리(완료기록은 항상 보존). 2주 후 자동 완전삭제 기능도 루틴에서는 제거
- 루틴을 삭제했다가 복구하면, 삭제돼 있던 기간을 "건너뛴 날짜"로 자동 채워 넣어서 스트릭이 억울하게 끊기지 않도록 함(기존 "특정 날짜 건너뛰기" 기능 재사용)
- 통계에 "역대 최고 기록"(지금까지 있었던 모든 루틴을 통틀어 가장 길었던 스트릭 하나) 개념을 새로 만들어서, 루틴을 지워도 그 기록만은 남도록 함 — 캘린더 주간뷰 위에 배지로 표시
- **캘린더 화면 전면 개편**: 기본 화면을 월간뷰에서 주간뷰로 변경, 다른 탭 갔다가 돌아오면 항상 주간뷰+이번 주로 리셋, 오늘 날짜가 화면 가운데쯤 보이도록 자동 스크롤, "월" 버튼을 누르면 항상 실제 이번 달로 리셋, 로딩 스피너를 완전히 없애고 데이터가 도착하는 대로 화면이 채워지는 방식으로 변경, 이미 봤던 달/주는 재요청은 하되 화면은 안 건드리다가 조용히 최신화(Stale-While-Revalidate)
- `CalendarList`의 기본 준비 범위(과거/미래 각 50개월)를 24개월/12개월로 줄여서 초기 로딩 부담을 줄임

### 왜 이렇게 했는지

- **완전삭제 정책을 통째로 바꾼 이유**: 원래는 "휴지통에서 2주 기다리지 않고 즉시 완전삭제"가 가능한 기능이 있었는데, 이게 실제로 DB에서 루틴 행을 지워버리는 방식이라 연결된 완료 기록도 자동으로 같이 사라졌음(CASCADE 삭제). 사용자가 "루틴을 그만 쓰는 것"과 "그동안 쌓은 기록을 지우는 것"은 서로 다른 결정이라고 판단했고, 완전삭제가 있으면 실수로 몇 달치 기록을 영영 잃을 위험이 있어서, 아예 "루틴은 절대 완전히 안 지운다"는 더 단순하고 안전한 규칙으로 바꿈. 모음집(템플릿)은 완료 기록이 안 달려있어서 완전삭제를 그대로 남겨둬도 안전함
- **"생성일 이전 날짜 제외" 로직을 뺐다가 다시 넣은 이유**: 처음에 "삭제해도 과거 기록 유지"를 고치면서 "생성일 이전 날짜는 제외"와 "삭제일 이후는 제외"를 한꺼번에 추가했는데, 그 직후 "이전 데이터가 다 사라졌다"는 문제가 생겨서 원인을 좁히려고 생성일 체크만 뺐음. 나중에 새 루틴을 만들었더니 몇 달~몇 년 전 날짜에도 다 예정된 것처럼 나오는 걸 발견하고서야, 생성일 체크가 애초에 꼭 필요한 로직이었다는 게 확인되어 다시 넣음 — 문제를 좁혀서 해결하는 과정에서 진짜 원인이 아닌 걸 먼저 없앴다가 되돌린 사례
- **캘린더 로딩 스피너를 완전히 없앤 이유**: 사용자가 "로딩 화면이 계속 보여서 쓰기 불편하다"고 명확히 요청했음. 데이터가 없어도 날짜 칸 자체는 항상 그릴 수 있으니(색이나 일정만 나중에 채워지는 것), 스피너로 화면을 막을 필요가 없다고 판단해서 아예 없애고 "빈 칸 → 채워짐" 방식으로 바꿈
- **"오늘 날짜가 화면 가운데 안 보인다"는 문제가 반복됐던 이유**: 처음엔 주의 시작일 자체를 오늘 기준 3일 전으로 바꿔봤는데(일~토가 아니게 됨) 요일 라벨이 꼬이는 새 버그가 생겨서, 결국 주는 전통적인 일~토 그대로 두고 "가로 스크롤 위치"만 계산해서 오늘 칸이 보이게 당기는 방식으로 바꿈. 그마저도 처음엔 스크롤 명령이 화면이 실제로 그려지기 전에 너무 일찍 실행돼서 무시되는 타이밍 문제가 있었음(레이아웃이 끝난 뒤에 실행하도록 고쳐서 해결)

## 2026-08-29~31 — 데이터 레이어 표준화(react-query 도입) + QA 버그 다수 수정

### 오늘 한 일 요약

폰으로 계속 테스트하다 보니 "화면 깜빡임", "다른 탭 갔다 왔는데 안 새로고침됨", "체크할 때 살짝 렉 걸림" 같은 자잘한 버그가 반복적으로 나왔습니다. 원인을 파고들어 보니 도메인(데이터 구조) 문제가 아니라, 화면마다 "서버에서 데이터를 언제/어떻게 다시 불러올지"를 각자 손으로 짜다 보니 방식이 미묘하게 달라서 생긴 문제였습니다. 그래서 **`react-query`라는 표준 라이브러리로 데이터 불러오기/캐싱 방식을 앱 전체에 통일**하는 큰 리팩터링을 진행했고, 기존 기능을 하나도 잃지 않았는지 체크리스트를 만들어가며 화면을 하나씩 옮겼습니다. 그 이후엔 폰으로 실기 QA를 여러 라운드 돌며 트래킹 기록 UI, 슬롯(아침/점심 등) 시간 설정, 모음집 중복 생성 버그, 타임라인 표시 등 자잘한 버그를 계속 찾아 고쳤고, 구글 로그인 테스트가 막히는 문제를 USB 연결(`adb reverse`)로 우회하는 방법도 새로 익혔습니다.

### 오늘 나온 개념 정리 (쉬운 설명)

| 용어 | 쉬운 설명 |
| --- | --- |
| react-query (서버 상태 관리 라이브러리) | "서버에서 받아온 데이터를 언제 다시 불러올지, 화면 여러 개가 같은 데이터를 어떻게 공유할지"를 대신 관리해주는 라이브러리. 예전엔 이걸 화면마다 직접 `useEffect`로 손으로 짰는데, 화면마다 조금씩 다르게 짜여서 버그가 반복됐음 |
| 쿼리 키(query key) | react-query가 데이터를 저장해두는 "이름표" 같은 것. 예를 들어 `['slots', 유저id]`라는 같은 이름표를 여러 화면이 쓰면, 한 화면에서 받아온 값을 다른 화면도 그대로 재사용함(캐시 공유) |
| 캐시 무효화(invalidate) | "이 데이터는 이제 오래됐으니 다음에 보여줄 때 새로 받아와라"라고 표시해두는 것. 예를 들어 모음집을 적용하면 "내 루틴" 목록도 같이 무효화해서, 그 화면에 갔을 때 최신 상태로 보이게 함 |
| 낙관적 업데이트(optimistic update) | 서버 응답을 기다리지 않고 화면부터 먼저 바꿔서 보여주는 기법. 체크박스를 눌렀을 때 서버 응답이 오기 전까지 화면이 안 바뀌어서 "렉 걸린다"고 느껴지던 문제를, 일단 화면부터 바꾸고 실패하면 되돌리는 방식으로 해결함 |
| 오프라인 캐시(persist) | 앱을 완전히 껐다 켜도 마지막으로 받아온 데이터를 잠깐 보여줄 수 있게, 캐시를 폰 저장공간(AsyncStorage)에도 같이 저장해두는 기능 |
| JSON 직렬화의 한계 | 자바스크립트의 `Map`/`Set`이라는 자료구조는 JSON으로 저장했다가 다시 불러오면 빈 객체(`{}`)로 망가짐. 이번에 캘린더 탭과 "내 루틴" 탭이 각각 이 문제로 실제로 크래시가 났었고, 둘 다 "이 데이터는 디스크에 저장하지 말 것" 목록에 추가해서 해결함 |
| RLS(Row Level Security, 행 단위 보안) | 데이터베이스 자체가 "이 계정은 자기 것만 조회/수정 가능"하게 걸어두는 규칙. 덕분에 앱 코드에서 매번 "내 유저ID인지" 확인하는 조건을 안 붙여도 자동으로 안전하게 걸러짐 |
| adb reverse (USB 포트 포워딩) | 폰과 PC를 USB로 연결해서, 폰이 PC의 특정 포트를 마치 자기 자신(`localhost`)인 것처럼 접속할 수 있게 해주는 안드로이드 개발 도구. 구글 로그인이 와이파이 터널 방식에서 리다이렉트가 막히는 버그를 피하려고 이번에 새로 사용함 |

### 확정한 결정

- 오늘/캘린더/통계 탭과 나머지 화면(즐겨찾기, 모음집, 내 루틴, 루틴 복구, 영상, 설정, 일기, 루틴 폼 등) **전부를 react-query 기반으로 통일**. 여러 화면이 같은 쿼리 키(`slots`, `favorites`, `stats`, `presets` 등)를 공유해서, 한 화면에서 바꾼 게 다른 화면에도 자동 반영됨
- 체크박스 토글·트래킹 저장·오늘 삭제 3가지 동작에 **낙관적 업데이트** 적용 — 서버 응답 기다리지 않고 화면부터 바로 바뀌게 해서 "체크할 때 렉 걸린다"는 문제 해결
- **트래킹형 루틴에 "취소"(기록삭제) 기능 신규 추가** — 예전엔 체크형만 다시 눌러서 기록을 지울 수 있었는데 트래킹형은 못 지웠음. 기록이 있으면 "✓ 오늘 기록 N" + 수정/기록삭제 버튼으로, 없으면 입력창+저장 버튼으로 화면이 바뀌게 해서 저장됐는지 눈으로 바로 확인 가능하게 함
- **트래킹 입력창이 화면 아래쪽에 있을 때 키보드에 가려지는 버그 수정** — 입력창에 포커스되면 그 줄을 화면 위쪽으로 당겨오고, 키보드가 완전히 다 올라온 시점에 한 번 더 강제로 위치를 맞춤(안드로이드 ScrollView의 기본 자동 스크롤 동작이 우리가 옮긴 위치를 다시 밀어버리는 문제가 있었음)
- **슬롯(아침/점심/저녁/자기전)에 "체크형"(정확히 그 순간만 체크) / "정확한 시간"(범위) 타입 신규 추가**. 기본은 체크형, 신규 가입자는 아침7시/점심12시/저녁18시/자기전22시로 기본 설정. 모드를 왔다갔다 해도 한 번 커스텀한 시간은 유지됨(값을 안 건드리고 모드 플래그만 바꾸는 방식으로 구현)
- **모음집 "오늘 목록에 적용" 버튼의 중복 생성 버그 수정**: 이미 그 모음집으로 만든 루틴이 있으면(일시정지 상태 포함) 새로 만들지 않고 일시정지만 풀어서 재사용하도록 변경 — 예전엔 "전체 비활성화" 후 다시 "적용"을 누르면 개수가 계속 불어났음(2개→4개)
- **오늘 탭에서 스와이프로 "오늘 삭제"한 루틴을 되돌리는 기능 신규 추가**: "내 루틴" 화면에 "오늘 제외됨" 표시 + "오늘 목록에 추가" 버튼
- **타임라인에서 슬롯이 "정확한 시간"으로 설정돼 있으면 그 시간대 길이만큼 실제 높이로 블록을 그림**(체크형이면 기존처럼 작은 점 블록 유지) — 정확한 시각 루틴과 똑같은 방식으로 통일
- 슬롯 선택 칩(루틴/모음집/즐겨찾기 폼 공통)에 "아침" 옆에 실제 시각도 같이 표시(`slotTimeLabel` 헬퍼)
- 설정 화면 슬롯 시계도 다른 화면과 같은 스피너 방식(15분 단위)으로 통일, 설명 문구는 최초 1회만 자동으로 보여주고 그다음부턴 ⓘ 아이콘으로 접힘(체크형/정확한 시간 안내, 메모 알림 안내 둘 다)
- 구글 로그인 테스트가 막힐 때(와이파이 터널 방식 ngrok이 구버전이라 서버에서 거부됨) **USB + `adb reverse` 방식으로 우회** — `adb reverse tcp:포트 tcp:포트` 실행 후 Expo Go에서 `exp://localhost:포트`로 수동 접속하면 리다이렉트 버그를 안 타서 정상 로그인됨. 평소 개발은 이 방식 필요 없고 와이파이 QR 스캔으로 충분

### 왜 이렇게 했는지

- **react-query로 갈아탄 이유**: 화면 깜빡임·중복 요청·안 새로고침되는 버그가 매번 조금씩 다른 원인으로 반복됐는데, 공통점을 짚어보니 "포커스될 때 다시 불러오기"를 화면마다 직접 손으로 짜서 생기는 문제였음. 표준 라이브러리로 통일하면 이런 종류의 버그 자체가 구조적으로 없어짐. 마이그레이션 전에 기존 기능을 전부 적어둔 체크리스트(`docs/data-layer-migration-checklist.md`)를 먼저 만들고, 화면 하나 옮길 때마다 그 체크리스트와 대조해서 기능이 안 빠졌는지 확인하는 방식으로 진행함 — 실제로 이 과정에서 "조회 실패 시 에러 메시지가 안 뜨는" 회귀, "캘린더가 안 보이는 뷰까지 같이 요청하는" 회귀 2가지를 직접 찾아 고쳤음
- **`Set`/`Map` 데이터를 디스크에 저장하면 안 되는 이유**: 자바스크립트의 이 두 자료구조는 JSON으로 바꿨다가 되돌리면 내용이 사라지는데, 겉보기엔 멀쩡해 보이다가 그 값에 `.get()`/`.has()` 같은 메서드를 부르는 순간에야 "함수가 아니다"라며 에러가 남 — 처음 캘린더 탭에서 이 문제로 크래시가 났고, 원인을 안 뒤에도 이번에 새로 추가한 "오늘 제외됨" 기능이 똑같은 실수로 또 "내 루틴" 탭을 크래시내서, 앞으로 비슷한 데이터를 추가할 때 반드시 확인할 목록으로 코드에 주석까지 남겨둠
- **슬롯 모드 전환 시 시간을 초기화했다가 다시 되돌린 이유**: 처음엔 "정확한 시간"으로 처음 바꿀 때 보기 좋으라고 기본값(아침 7-8시 등)을 자동으로 채워주게 만들었는데, 이 로직이 전환할 때마다 매번 실행되는 바람에 사용자가 직접 6-7시로 고쳐놔도 체크형 갔다가 다시 오면 7-8시로 리셋돼버리는 부작용이 있었음. "한번 정한 값은 계속 유지돼야 한다"는 피드백을 받고, 아예 전환 로직에서 시간 값은 안 건드리고 모드 플래그만 바꾸는 걸로 단순화함 — 신규 가입자는 가입할 때부터 이미 괜찮은 기본값이 들어있어서, 자동으로 채워주는 로직이 없어도 문제없음

### 새로 나온 개념 정리 (쉬운 설명)

| 개념 | 쉬운 설명 |
|---|---|
| 안드로이드 그림자+모서리 둥글기 클리핑 버그 | 리액트 네이티브에서 안드로이드는 `borderRadius`(모서리 둥글기)와 그림자를 같은 화면 요소 하나에 같이 주면, 그림자가 모서리 밖으로 그려지려다가 그 요소 자체의 둥근 테두리에 잘려서 안 보이게 되는 버그. iOS는 이 문제가 없어서 더 헷갈리기 쉬움 |
| 2계층(바깥/안쪽) 그림자 컴포넌트 패턴 | 위 버그를 피하려고, "그림자만 그리는 네모난 바깥 껍데기"와 "모서리를 둥글게 깎고 실제 내용을 담는 안쪽 상자"를 별도의 화면 요소 두 개로 나누는 방법. 안쪽 상자가 모서리를 담당하니 바깥 껍데기의 그림자는 잘릴 일이 없음 |
| includeFontPadding (안드로이드 전용) | 안드로이드가 글자 위아래에 기본으로 넣는 여유 공간. 이게 켜져 있으면(기본값) 버튼 안 글자가 상자 정중앙이 아니라 살짝 아래로 처져 보일 수 있어서, 정확히 가운데 맞추고 싶을 때는 꺼줌 |
| 고정폭 슬롯으로 가운데 정렬 | 버튼마다 글자 수가 달라 너비가 제각각이면(예: "저장" vs "✓ 5잔") 화면에서 세로로 나열했을 때 중심이 안 맞아 보임. 이럴 때 내용물을 감싸는 상자의 너비를 미리 고정값(예: 56px)으로 정해두고 그 안에서 가운데 정렬하면, 내용물 너비와 상관없이 상자의 중심이 항상 같은 위치에 오게 됨 |
| 클러스터/컬럼 배치 | 타임라인처럼 여러 일정이 같은 시간대에 겹칠 수 있는 화면에서, 겹치는 것들끼리 묶어서(클러스터) 옆으로 나란히 배치하거나 순서대로 쌓는 방식. 이번엔 "겹치면 무조건 작은 고정 높이로" 뭉개던 부분을 "겹쳐도 각자 원래 소요 시간만큼의 높이는 유지"하도록 고침 |
| React Navigation 테마 오버라이드 | 화면 자체의 배경색은 앱이 직접 관리하는 색상표(`Colors.ts`)로 정하지만, 화면 전환 애니메이션이나 탭 전환 시 아주 짧게 보이는 배경은 내비게이션 라이브러리(React Navigation)가 자기 자신의 기본 테마 색을 따로 갖고 있어서, 이 둘이 다르면 전환 순간에 색이 잠깐 튀어 보임. 라이브러리의 테마 색도 앱 색상표와 똑같이 맞춰서 해결함 |

### 왜 이렇게 했는지

- **그림자가 몇 번을 값만 바꿔도 안 보였던 이유**: 처음엔 `shadowOpacity`/`elevation` 수치를 6번 넘게 바꿔가며 시도했는데 전혀 효과가 없었음. 알고 보니 값 문제가 아니라 안드로이드가 "모서리 둥근 상자에는 그림자를 그 상자 테두리 안쪽으로 잘라버리는" 구조적인 버그였고, 값을 아무리 키워도 애초에 안 그려지는 게 아니라 그려진 뒤 잘려서 안 보이는 것이었음. 그림자 전용 레이어와 모서리 전용 레이어를 분리하고 나서야 아주 극단적인 값(`shadowOpacity:1`)으로 실제 렌더링이 되는 걸 확인했고, 그다음 정상적인 값으로 되돌려 마무리함
- **버튼 가운데 정렬을 세 번 다시 고친 이유**: 처음엔 체크박스와 저장 버튼을 감싸는 상자를 56px 고정폭으로 만들어 가운데 정렬했는데, 그다음 요청은 "체크박스가 원래 있던 자리(더 오른쪽) 기준으로 맞춰달라"는 것이어서 상자 폭을 체크박스와 똑같은 28px로 줄였음 — 그런데 이러면 "저장" 버튼처럼 28px보다 넓은 내용물이 좁은 상자에 눌려서 찌그러지는 부작용이 생김. 결국 "안 깨지는 것"과 "가운데가 딱 맞는 것" 중 안 깨지는 쪽을 먼저 만족시켜야 한다는 걸 확인하고, 버튼이 여유 있게 들어가는 56px 고정폭으로 되돌려 마무리함 — 값을 키우고 줄이는 시행착오 끝에 "내용물이 상자보다 항상 작아야 가운데 정렬이 안전하다"는 원칙을 확인한 사례
- **타임라인 "겹치면 작아지는" 버그를 찾은 과정**: 처음엔 "특정 루틴 하나만 반 토막으로 보인다"는 제보를 받고 그 루틴 하나의 데이터(시각 체크 여부 등)를 의심하며 코드를 팠지만 이상이 없었음. 사용자에게 "세로 높이가 문제냐, 가로 폭이 문제냐"를 다시 확인받은 뒤 "같은 시간대에 2개가 있으면"이라는 힌트로 재현 조건을 좁혔고, 그제서야 "겹치는 일정끼리 화면을 나눠 보여주는" 로직 안에서 실수로 모든 겹친 일정의 높이를 원래 소요 시간과 상관없이 작은 고정값(34px)으로 강제하고 있던 부분을 발견함 — 증상을 짐작으로 좁히기보다 사용자에게 정확히 어떤 축(가로/세로)이 문제인지 되물은 게 실제 원인을 찾는 데 결정적이었음

### 새로 나온 개념 정리 (쉬운 설명)

| 개념 | 쉬운 설명 |
|---|---|
| 절대 위치(position: absolute) 배치 | 화면 요소를 "위에서부터 순서대로 쌓기"가 아니라 "화면의 몇 %/몇 px 지점에 딱 고정"시키는 방식. 콘텐츠 길이가 짧든 길든 항상 정해진 위치에 오기 때문에, 이번처럼 "콘텐츠가 짧으면 간격이 이상해지는" 문제를 피할 수 있음 |
| React Context (전역 공유 상태) | 여러 화면이 같은 값을 "실시간으로" 함께 봐야 할 때 쓰는 방법. 이번 온보딩 버그의 원인이 정확히 이거였음 — 화면(레이아웃)이 값을 딱 한 번만 읽고 그 이후 변화를 모르고 있었던 게 문제였는데, Context로 바꾸면 어디서 값이 바뀌든 그걸 보고 있는 모든 화면이 즉시 같은 값을 보게 됨 |
| 확정 전 미리보기(로컬 state) vs 즉시 저장(전역 state) | 설정 화면처럼 "누르면 바로 적용"되어야 하는 곳과, 온보딩처럼 "확정 버튼을 눌러야만 적용"되어야 하는 곳은 저장 시점이 달라야 함. 같은 선택 UI라도 화면 자체의 임시 기억공간(로컬 state)에만 담아뒀다가, 확정 버튼을 눌렀을 때만 진짜 저장소(전역 상태+기기 저장소)에 옮겨 담는 방식으로 구분함 |
| 스와이프 인스턴스에 직접 명령 내리기(ref) | 화면에 그려진 컴포넌트 하나하나를 "리모컨"처럼 직접 조작하고 싶을 때 쓰는 방법(`ref`). 이번엔 리스트의 각 행(스와이프 가능한 카드)마다 리모컨을 하나씩 만들어뒀다가, "수정" 버튼을 누르면 그 행의 리모컨한테 직접 "닫혀라"라고 명령을 내리는 방식으로 구현함 |

### 확정한 결정

- **온보딩 화면 4개 그룹 위치를 화면 높이의 22% / 42% / 62% / 82% 지점에 고정** — 콘텐츠 길이와 무관하게 항상 이 위치에 오도록 함. 대신 테마색 원(44→56px), 폰트 버튼 패딩 등 콘텐츠 자체의 크기를 키워서 구간이 넓어져도 빈 공간처럼 안 보이게 함
- **온보딩에서 선택은 "로컬 미리보기 → 확정 시에만 실제 저장"으로 구조 변경**: 확정 안 하고 나가면 다음에 다시 들어왔을 때 원래 기본값(구름색 테마 + 동글 폰트)으로 보이는 게 맞는 동작으로 확정
- **온보딩 완료 여부를 `lib/onboarding.tsx`의 Context(`OnboardingProvider`/`useOnboarding`)로 전환** — `app/_layout.tsx`가 이 값을 실시간으로 구독해서, 온보딩에서 저장하는 즉시 다시 온보딩으로 안 튕기도록 함
- **오늘 탭 에러 배너는 2초 뒤 자동으로 사라지고, 파스텔 빨강 배경+흰 텍스트+앱 폰트를 쓰는 배너 스타일로 통일**
- **리스트 스와이프는 "수정"/"기록삭제" 액션 후 자동으로 닫히고, 그 루틴이 보이는 위치로 스크롤 이동. 스와이프를 열어두고 2초 방치하거나 다른 탭에 갔다 오면 자동으로 닫힘**

### 왜 이렇게 했는지

- **레이아웃을 "남는 공간 분배"에서 "절대 위치 고정"으로 바꾼 이유**: 처음 방식(`justifyContent: 'space-between'`)은 이론상 맞아 보였지만, 실제 콘텐츠(스와치 5개, 버튼 2개 등)가 화면에 비해 짧다 보니 분배할 "남는 공간" 자체가 컸고, 그 큰 공간이 소수의 그룹 사이에만 몰려서 오히려 "듬성듬성 떠 있는 섬" 처럼 보이는 역효과가 났음. 콘텐츠 길이에 의존하지 않는 절대 위치 방식으로 바꾸고 나서야 예측 가능한 결과를 얻을 수 있었음
- **무한 루프 버그를 Context로 고친 이유**: 처음엔 "시작하기 버튼이 안 눌리나?" 싶었지만, 실제로는 버튼도 눌리고 저장도 됐고 화면 전환(`router.replace`)도 실행되고 있었음 — 문제는 그 다음이었음. 상위 레이아웃(`_layout.tsx`)이 "온보딩을 봤는지" 여부를 화면 진입 시 딱 한 번만 저장소에서 읽어와 자기만의 복사본(로컬 state)으로 갖고 있었기 때문에, 온보딩 화면이 저장소에 새 값을 써넣어도 레이아웃의 복사본은 여전히 옛날 값(안 봄)이었음. 그래서 `/(tabs)`로 넘어가자마자 레이아웃이 "어? 아직 온보딩 안 봤네?" 하고 다시 온보딩으로 돌려보내는 루프가 생겼음. 이걸 고치려면 "복사본을 다시 읽어오게" 하는 게 아니라, 애초에 복사본을 안 만들고 원본 하나(Context)를 같이 보게 만드는 게 근본적인 해결책이었음
- **확정 전 미리보기 방식을 도입한 이유**: 사용자가 실제로 폰에서 테스트하다가 "테마색을 눌러만 봤는데 확정 안 하고 나갔는데도 그 색이 남아있다"는 문제를 발견했음. 원인은 설정 화면과 똑같은 "누르면 바로 저장" 함수를 온보딩에도 그대로 재사용했기 때문이었는데, 온보딩은 성격이 달라서(둘러보기 vs 확정) 저장 시점을 분리해야 했음

## 2026-09-06 — 온보딩을 "계정당 1회"로 서버 저장 전환 + 로그인/로그아웃이 안 되던 심각한 라우팅 버그 발견 및 수정

### 오늘 한 일 요약

시작은 단순했습니다. Expo Go 앱이 최신 버전(SDK 57)으로 자동 업데이트되면서 이 프로젝트(SDK 54)와 버전이 안 맞아 실행이 안 되는 문제부터 해결했고(구버전 Expo Go APK를 따로 설치), 이어서 구글 로그인 테스트 중 "온보딩(테마색/폰트 선택 화면)이 같은 계정으로 다시 로그인해도 매번 다시 뜨는" 문제를 발견했습니다. 원인은 온보딩을 봤는지 여부가 폰 로컬 저장소에만 저장돼 있어서 "기기당 1회"로 동작하고 있었기 때문이었습니다. 이걸 서버(계정)에 저장하도록 구조를 바꿨습니다.

그런데 이 변경을 테스트하는 과정에서 훨씬 심각한 문제가 터졌습니다. 로그인은 되는데 "내 루틴", "캘린더" 화면에 데이터가 하나도 안 보이고, 통계 탭은 계속 로딩만 돌고, 설정 화면엔 이메일도 안 뜨고, 로그아웃 버튼을 눌러도 화면이 안 바뀌는 상황이 벌어졌습니다. 처음엔 "루틴 84개가 정말 다 지워진 건 아닐까"까지 걱정했지만, Supabase 대시보드에서 직접 SQL로 확인해서 루틴 데이터는 서버에 84개 그대로 안전하게 있다는 걸 먼저 확인했습니다(이 확인이 이후 안심하고 계속 디버깅할 수 있었던 중요한 지점이었습니다).

이후 몇 시간에 걸쳐 Expo Go 재설치, USB 연결(adb), 네트워크 확인, 서버 세션 강제 삭제 등 여러 시도를 거치며 원인을 좁혀갔고, 최종적으로 코드에 직접 진단용 로그를 심어서 "지금 로그인 세션에 정말 무슨 값이 들어있는지"를 눈으로 확인하는 방법으로 진짜 원인을 찾아냈습니다. 결론은: **세션은 이미 제대로 로그아웃된 상태(정상)였는데, 화면이 로그인 화면으로 넘어가는 코드 자체가 실행되지 않는 버그**가 있었던 것입니다. 이 버그를 고치고 나니 로그인/로그아웃이 정상 동작했고, 그 과정에서 발견한 또 다른 버그(화면에 다시 들어올 때 새로고침하는 기능이 로그인 정보가 준비되기 전에 실행돼서 서버 에러를 내던 문제)도 8개 화면에 걸쳐 함께 고쳤습니다.

### 새로 나온 개념 정리 (쉬운 설명)

| 개념 | 쉬운 설명 |
|---|---|
| 세션(session) | "지금 로그인돼 있다"는 증명서 같은 것. 로그인하면 서버가 발급해주고, 앱은 이걸 기기에 저장해뒀다가 매 요청마다 같이 보내서 "나 이 사람 맞아요"를 증명함. 이게 없으면(null) 로그아웃된 상태 |
| enabled 옵션 (데이터 조회 라이브러리) | "이 조건이 참일 때만 서버에 물어봐라"는 안전장치. 예: `enabled: 로그인정보가있을때만`. 로그인 정보가 없는데 조회를 시도하면 의미 없는 값(undefined)으로 서버에 물어보게 되고, 서버는 "그런 값은 형식이 이상해요"라며 에러를 냄 |
| 안전장치를 우회하는 수동 새로고침 | 위 `enabled` 안전장치는 "화면이 처음 열릴 때 자동으로 물어보는 것"만 막아줄 뿐, 코드에서 "지금 당장 다시 물어봐!"라고 직접 명령하는 수동 새로고침(refetch)에는 적용되지 않는 경우가 있음. 이번 버그가 정확히 이 틈새였음 — "다른 탭 갔다 돌아오면 새로고침" 기능이 이 수동 명령 방식이라 안전장치를 그냥 지나쳐버렸음 |
| 라우팅 가드(routing guard) | "지금 상태에 따라 어느 화면으로 보낼지" 결정하는 코드. 예: "로그인 안 했으면 로그인 화면으로, 로그인했으면 홈 화면으로". 이번 버그는 이 가드 안에 있던 "일단 기다려라"는 조건이 로그아웃 상태에서도 걸려버려서, 정작 "로그인 화면으로 보내라"는 코드까지 도달을 못 하고 있었던 것 |
| adb reverse (USB 포트 연결) | 폰과 PC를 USB로 연결해서, 폰이 "PC의 특정 포트"를 자기 자신의 포트인 것처럼(`localhost`) 접속할 수 있게 다리를 놓아주는 명령. 와이파이 터널 방식이 막힐 때 쓰는 대안 |
| Postgres uuid 타입 에러 | 데이터베이스의 어떤 칸이 "고유 식별번호(uuid)만 들어올 수 있어요"라고 정해져 있는데, 거기에 진짜 값 대신 실수로 문자 그대로의 "undefined"라는 글자가 들어가면 데이터베이스가 "이건 그 형식이 아니에요"라며 거절하는 에러. 이게 뜨면 대부분 "서버에 물어봐야 할 값이 아직 준비 안 됐는데 성급하게 물어봤다"는 신호 |

### 확정한 결정

- **온보딩 완료 여부를 `users` 테이블의 `onboarding_completed` 컬럼(서버 저장)으로 전환** — 이제 계정 기준으로 1회만 보여지고, 기기를 바꾸거나 앱을 재설치해도 유지됨(마이그레이션 `0025_add_onboarding_completed.sql`)
- **라우팅 가드 수정**: "온보딩 정보를 기다리는" 조건은 로그인된 상태에서만 적용하도록 변경(`app/_layout.tsx`) — 로그아웃 상태에서 로그인 화면으로 못 가던 버그의 근본 원인
- **"화면 복귀 시 새로고침" 기능에 안전장치 추가**: `lib/use-refetch-on-focus.ts`에 `enabled` 매개변수를 추가해서, 로그인 정보가 없을 땐 새로고침을 건너뛰도록 수정하고, 이걸 쓰는 8개 화면(오늘/통계/캘린더/내 루틴/즐겨찾기/모음집/루틴 복구/영상 카테고리) 전부에 적용
- **통계 화면의 "로딩 중"과 "조회 실패"를 구분**: 예전엔 조회가 실패해도 무조건 로딩 스피너만 계속 보여서 마치 무한 로딩처럼 보였는데, 이제 실패 시엔 "다시 시도" 버튼이 있는 별도 화면을 보여줌

### 왜 이렇게 했는지

- **"루틴 84개가 다 사라졌다"고 걱정했지만 실제로는 안전했던 이유**: 화면에 데이터가 하나도 안 보이면 "데이터가 지워졌다"고 오해하기 쉽지만, 이번 경우처럼 "조회 자체가 실패해서 빈 화면처럼 보이는 것"과 "진짜로 데이터가 없는 것"은 겉보기엔 똑같아 보임. Supabase 대시보드에서 SQL로 서버에 직접 물어봐서 실제로 데이터가 있는지부터 확인한 게, 불필요하게 겁먹지 않고 침착하게 진짜 원인(조회 실패)을 찾아갈 수 있었던 결정적 단계였음
- **진단 로그를 코드에 직접 심어서 확인한 이유**: 여러 시도(재설치, USB 연결, 서버 세션 삭제 등)를 해도 증상이 안 바뀌자, 추측만으로는 한계가 있다고 판단해 "지금 이 순간 세션 값이 정확히 뭔지"를 코드로 직접 출력해서 눈으로 확인하는 방법을 씀. 그 결과 "세션이 이상한 값(문자열 undefined)"이 아니라 "세션이 아예 없음(null, 정상적인 로그아웃 상태)"이라는 걸 확인했고, 이 한 번의 확인이 "세션이 깨졌다"는 잘못된 가설을 버리고 "그럼 왜 로그인 화면으로 안 넘어가지?"라는 진짜 질문으로 방향을 바꾸게 해줌
- **온보딩 변경이 이 버그의 도화선이었던 이유**: 온보딩을 서버 저장으로 바꾸면서 "로그아웃 상태에서는 서버에 물어볼 계정 자체가 없다"는 새로운 경우의 수가 생겼는데, 기존 라우팅 코드의 "일단 기다려라" 조건이 이 경우까지는 고려하지 않고 있었음. 새 기능을 추가할 때 "이 상태값이 가질 수 있는 모든 경우(로그인/로그아웃 등)"를 다시 점검해야 한다는 걸 보여준 사례
