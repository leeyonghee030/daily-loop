# Daily Loop — 프로젝트 기획 확정 문서

> 이 문서는 "Daily Loop" 루틴 관리 앱의 기획 단계에서 확정된 모든 결정을 정리한 것입니다. 나중에 새 대화를 시작하거나, Claude Code 등 개발 도구에 프로젝트 맥락을 전달할 때 이 문서 전체를 붙여넣으면 처음부터 다시 설명할 필요 없이 이어서 작업할 수 있습니다.
> 
> 최종 업데이트 기준: 기획 논의 종료 시점 (개발 착수 전)

---

## 1. 한눈에 보는 프로젝트 개요

|항목|내용|
|---|---|
|앱 이름|**Daily Loop** — 부제: "매일 루틴 관리"|
|한 줄 정체성|말하듯 텍스트 한 줄 적으면 루틴이 자동으로 짜지는, 가장 빠르고 편한 루틴 앱|
|타겟 유저|10~30대, 갓생 살려고 매일 루틴을 폰으로 편하게 적는 사람|
|개발자|1인 개발, 바이브 코딩으로 직접 만들며 학습 병행|
|개발 목표|배우면서 만들고, 작지만 실제로 돈이 되는 사업으로 운영|

---

## 2. 핵심 차별화 전략 (반드시 기억할 것)

이 앱의 유일하고 진짜 강점은 **"UI가 깔끔하다"가 아니라 LLM 자연어 → 루틴 자동 배치 기능**입니다. 기능 개수로는 기존 대형 루틴 앱(Habitica, 챌린저스, Finch 등)을 절대 이길 수 없다는 걸 전제로 하고, 이 한 가지 기능에 제품 정체성을 집중시키기로 결정했습니다.

새로운 기능을 추가할지 고민될 때마다 **"이게 이 핵심 정체성을 더 강하게 만드는가?"**를 기준으로 판단할 것.

## 3. 기술 스택

|분류|선택|비고|
|---|---|---|
|프레임워크|**React Native**|React 문법 재사용 가능|
|IDE|**VS Code**|이미 사용 중인 에디터를 그대로 사용 (실제 코드 작성은 Claude Code가 터미널에서 수행하므로 에디터 자체는 코드 확인/터미널 용도, WebStorm 대비 무료·설치 부담 없음으로 변경 확정)|
|플랫폼|**안드로이드 우선**|등록비 저렴, 심사 빠름. iOS는 반응 보고 추후 확장|
|DB|**Supabase**|무료 티어, PostgreSQL(SQL) 기반 — 기존 SQL 학습 경험 재사용 가능|
|LLM|**Claude Haiku**|저렴한 소형 모델, 이 작업(텍스트 구조화)엔 충분|
|알림|**FCM (Firebase Cloud Messaging)**|무료|
|영상|**YouTube 임베드**|직접 제작 안 함, 저작권 준수 (아래 6번 참고)|

### 3-1. 로그인/인증 (신규 확정)

- **구글 로그인 + 카카오 로그인 둘 다 지원**으로 확정
- Firebase Auth는 구글은 기본 제공하지만 카카오는 기본 지원하지 않음 → 카카오 로그인 성공 후 발급받은 토큰으로 백엔드(Supabase Edge Function 등)에서 **Firebase Custom Token**을 발급해 연동하는 절차 필요 (구현 난이도 구글보다 높음, 일정에 반영 필요)
- 이메일/비밀번호 자체 회원가입은 지원하지 않음 (소셜 로그인만)

### 3-2. 삭제 정책 (신규 확정)

- 루틴 블록, 일기 등 사용자 데이터는 **소프트 삭제**로 확정 (`deleted_at` 컬럼에 삭제 시각 기록, 실제 row는 유지)
- 목록 조회 시 `deleted_at IS NULL` 조건으로 필터링
- 완료 기록(체크/트래킹 기록)은 통계 정합성을 위해 루틴이 삭제돼도 원본 기록은 남겨둠 (루틴 자체만 소프트 삭제 표시)

### LLM 연동 방식 (중요 — 비용 최적화 설계)

- 이건 RAG가 아니라 **"자연어 → 구조화된 JSON 출력"** 작업임
- 프롬프트에 few-shot 예시 넣어서 정확도 확보
- **하이브리드 구조 채택**: 정규식/키워드 사전으로 먼저 파싱 시도 → 애매한 경우만 LLM 호출 (비용 대폭 절감)
- **"100% 정확도"가 목표가 아님.** LLM이 만든 결과는 항상 "초안"이며, 사용자가 블록을 드래그/탭해서 바로 수정할 수 있는 UX로 설계 — 이게 정확도보다 더 중요한 설계 원칙
- 무료 버전에서는 **계정당 총 10회**로 호출 제한 (비용 리스크 관리, 동시에 핵심 기능 체험은 가능하게 하는 절충안)

### 정규식/키워드 사전 파싱 패턴 (초안 — 실사용 데이터로 계속 보강 예정)

**반복 패턴**

|입력 예시|파싱 결과|
|---|---|
|"매일"|daily|
|"평일", "주중", "평일마다"|weekday (월~금)|
|"주말", "주말마다"|weekend (토~일)|
|"월수금", "화목" 등 요일 조합|해당 요일 배열|
|"매주 화요일"|특정 요일 1개|
|(반복 표현 없음)|1회성|

**시간 패턴**

|입력 예시|파싱 결과|
|---|---|
|"아침 7시", "오전 7시"|07:00|
|"저녁 7시", "오후 7시", "19시"|19:00|
|"7시 30분", "7:30"|07:30|
|(시간 표현 없음)|슬롯 자동 배정 안 함 — 미리보기(4-8 ③)에서 사용자가 4개 슬롯 중 직접 선택 (신규 확정)|

**필수 키워드**: "꼭", "반드시", "필수로", "무조건" → 필수 토글 ON (미검출 시 기본 OFF)

**트래킹형 키워드**: "물 8잔", "팔굽혀펴기 30개", "책 20페이지", "달리기 3km", "명상 10분" 처럼 숫자+단위가 포함되면 트래킹형(4-6) 블록으로 생성 (목표치 판정은 안 하므로 단위만 참고용으로 추출)

이 사전으로 못 잡는 애매한 표현만 LLM으로 넘어가는 하이브리드 구조는 위와 동일.

## 4. 화면 구성 (와이어프레임 확정 완료)

### 4-1. 오늘 탭 (홈)

- 상단: 오늘 날짜 + 루틴 블록 리스트 (시간순, 시간·제목·반복정보 표시)
  - 시간이 지정된 블록은 시간순으로 배치
  - 시간 미지정 블록은 **시간대 슬롯**(아침/점심/저녁/자기전, 4-6 참고)에 배정되어 해당 슬롯 위치에 표시
- LLM 자연어 입력 배너 (상단, 잔여 횟수 표시 "N/10회")
- 각 블록: 체크 여부 표시, 영상 연결된 블록은 재생 아이콘 표시
  - 트래킹형 블록은 체크 대신 숫자 입력 UI 표시 (4-6 참고)
- **일기 쓰기 버튼** (블록 리스트 하단, 핑크 카드로 강조) — 오늘 하루 어땠는지 텍스트로 기록
- 하단: 오늘 완료율 + 연속 기록(스트릭) 요약
- **"지금 할 시간" 테두리 강조 (신규 확정)**: 정확한 시각(시작~종료 범위)이 지정된 블록만, 지금 시각이 그 범위 안이면 테두리 색으로 강조. 완료 체크를 했어도 범위 안이면 테두리 유지. 슬롯(아침/점심/저녁/자기전) 배정 블록은 범위가 넓어 의미가 약하므로 강조 대상에서 제외
- **공휴일 배너 (신규 확정)**: 오늘이 공휴일이면 상단에 배너로 공휴일 이름 표시 (예: "🎉 오늘은 설날이에요")

### 4-2. 캘린더 탭

- 월 단위 캘린더, **날짜별 컬러 코딩**:
    - 🟢 초록 = 그날 루틴 다 완료
    - 🟠 주황 = 일부만 완료
    - 🔴 빨강 = **"필수" 표시된 루틴을 놓친 날**
- 날짜 클릭 시 → 그날의 루틴 체크리스트 + 그날 작성한 일기가 하단에 펼쳐짐

### 4-3. 통계 탭

- 수행률, 스트릭 중심 (요일별 패턴/순위는 2차 이후 고려)

### 4-4. 루틴 블록 — 필수/선택 토글 (신규 확정)

- 루틴 블록을 만들 때 **"필수" 여부를 토글로 지정 가능**
- 필수로 지정한 루틴을 그날 못 하면, 캘린더에서 그 날짜가 빨간색으로 표시됨
- 이 토글이 캘린더 컬러 로직의 판단 기준이 됨 (구현 시 우선순위 높음)
- **홈 탭에서의 표시(신규 확정)**: 필수 블록은 제목 텍스트 뒤에 코랄(`#FF6B6B`) 반투명 형광펜 밴드를 살짝 삐뚤게 깔아 강조 — 색으로만 구분하던 기존보다 눈에 띄게. 토스 스타일(깔끔·모던) 기조는 유지하되 이 부분만 예외적으로 손글씨 형광펜 느낌 허용

### 4-11. 연속 성공 스트릭 이모지 (신규 확정)

같은 루틴 블록을 연속 며칠 성공했는지 **홈 탭에서만** 이모지로 표시 (캘린더 탭은 기존 컬러 코딩만 유지해 단순함 유지). **컨셉 변경(신규 확정)**: 돌멩이 진화 → "작은 물방울이 하나의 세계로 자라나는" 자연 요소(물·불·나무·구름 등) 컨셉으로 교체, 초반엔 주 단위로 촘촘하게 올라가다가 뒤로 갈수록 간격이 넓어져서 1년까지 이어지는 구성 (설정 테이블로 관리 — 나중에 구간/이모지 조정 쉬움):

|연속 기간|일수 기준|이모지|이름|
|---|---|---|---|
|1주 미만|1~6일|(표시 없음)|-|
|1주|7~13일|💧|작은 물방울|
|2주|14~20일|🌱|여린 새싹|
|3주|21~27일|🔥|타오르는 불씨|
|4주(1개월)|28~55일|☁️|떠오른 구름|
|8주(2개월)|56~90일|🌳|무성한 나무|
|13주(분기)|91~181일|🌈|피어난 무지개|
|26주(반년)|182~364일|🏔️|우뚝 선 산|
|52주(1년)|365일+|🌍|하나의 세계|

- 최소 표시 기준이 "2일"에서 "1주(7일)"로 상향됨 — 초반 진입장벽은 살짝 높아지지만, 이후 8단계로 세분화되면서 장기 동기부여가 더 촘촘해짐

### 4-5. 일기 기능 (신규 확정)

- **텍스트만** 지원 (사진 첨부 등은 하지 않음 — 저장 용량/비용 문제로 범위에서 제외)
- 날짜 하나당 일기 하나
- 캘린더에서 날짜 클릭 시 그날의 루틴 기록과 함께 조회 가능

### 4-6. 루틴 블록 타입 — 일반형/트래킹형 (신규 확정)

루틴 블록은 완료 방식에 따라 두 타입 중 하나로 생성됨:

|타입|완료 방식|기록되는 값|
|---|---|---|
|**일반형 (체크형)**|완료 버튼 탭|완료 시각이 자동 기록됨|
|**트래킹형 (수치 기록형)**|숫자 입력|입력한 숫자가 그대로 기록됨|

- 트래킹형은 **목표치 대비 달성 여부를 판정하지 않음** — 숫자를 입력하는 순간 그날은 "완료"로 처리, 입력값은 통계용 원시 데이터로만 저장 (판정 로직을 넣으면 루틴 제목마다 "많을수록 좋음/적을수록 좋음"이 달라 모호해지므로 단순화)
- 필수/선택 토글(4-4)은 트래킹형에도 동일하게 적용 — 필수 트래킹형 루틴에 숫자를 입력하지 않으면 캘린더에서 그 날짜가 빨간색으로 표시됨
- **단위 입력 UI (신규 확정)**: 잔/개/분/페이지/km 등 자주 쓰는 단위는 프리셋 버튼으로 제공, 목록에 없으면 자유 텍스트로 직접 입력 가능

### 4-7. 시간대 슬롯 (신규 확정)

- 시간을 지정하지 않은 루틴 블록은 **고정 4개 슬롯**(아침 / 점심 / 저녁 / 자기전) 중 하나에 배정
- 각 슬롯의 시간 범위는 설정 화면에서 사용자가 조정 가능 (슬롯 개수 자체는 커스텀 불가, 1차 버전 범위)
- **기본값 (초안)**: 아침 05:00–11:00 / 점심 11:00–15:00 / 저녁 15:00–21:00 / 자기전 21:00–05:00(익일)
- 홈 화면 루틴 리스트에서 슬롯 배정된 블록은 해당 슬롯 시간대 위치에 정렬되어 표시됨
- **슬롯별 알림 on/off (신규 확정)**: 4개 슬롯 각각에 독립적인 알림 토글 존재. 슬롯 알림이 켜져 있으면 해당 슬롯 시각에 "이 시간대 루틴 체크하세요" 알림 발송. 개별 루틴의 알림 토글(4-9)과는 별개 — 루틴 알림은 그 루틴 하나에 대한 것, 슬롯 알림은 시간대 전체에 대한 것
- **동일 시간 정렬 순서 (신규 확정)**: 같은 슬롯/같은 시각으로 묶인 루틴 블록끼리는 사용자가 드래그해서 순서를 직접 바꿀 수 있음 (정렬값 저장 필요 → ERD의 `sort_order` 참고)

### 4-12. FCM 알림 발송 설계 (신규 확정)

**알림 종류는 두 가지**

|종류|발송 조건|발송 시각|
|---|---|---|
|블록 알림|슬롯의 알림 토글이 ON|각 슬롯 시작 시각|
|리마인더 알림|그날 필수 루틴 중 미완료 항목이 1개 이상 있을 때만 발송 (다 했으면 발송 안 함)|"자기전" 슬롯 시작 시각 (기본 21:00, 사용자가 슬롯 시간 조정하면 그에 따름)|

- 발송 방식: 유저별 타임존을 고려해 Cloud Scheduler(또는 Cloud Functions cron)가 짧은 주기(예: 매 5분)로 "지금 시각과 일치하는 슬롯을 가진 유저"를 조회해 FCM 발송하는 배치 구조로 1차 버전 구현. 유저가 많아지면 슬롯 시각별 사전 큐잉 방식으로 전환 검토
- 리마인더 알림 판정을 위해 "오늘 필수 루틴 중 완료 기록이 없는 것이 있는가"를 빠르게 조회할 수 있어야 함 → ERD에서 완료 기록 테이블 인덱스 설계 시 반영

### 4-13. LLM 관련 안내 문구 / 오류 상태 화면 (신규 확정 — 카피만, 최종 문구는 UI 작업 시 다듬음)

- **사용법 안내**: LLM 입력 배너 첫 진입 시(또는 최초 1회) "하고 싶은 루틴을 편하게 말하듯 적어보세요. 예: 매일 아침 7시에 물 8잔 마시기" 형태의 툴팁/가이드 노출
- **횟수 소진 안내**: 잔여 횟수 0/10이 되면 배너 문구가 "이번 달 AI 배치 횟수를 모두 사용했어요. 루틴은 직접 추가할 수 있어요 →" 형태로 전환, 배너 탭 시 LLM 입력 대신 수동 추가 화면(4-9)으로 바로 이동
- **오류 상태 화면**: LLM 호출 실패/네트워크 오류 시 "지금은 AI 배치가 어려워요. 잠시 후 다시 시도하거나 직접 추가해주세요" + [다시 시도] [직접 추가] 두 버튼 제공 — 사용자가 막히지 않고 항상 수동 추가로 빠져나갈 수 있게 함

### 4-14. 설정 화면 진입 / 소급 수정 정책 / 기타 빈 상태 (신규 확정)

- **설정 진입 위치**: 오늘/캘린더/통계 3개 탭 공통 상단 헤더에 설정 아이콘 고정 — 특정 탭에 종속시키지 않고 어디서든 접근 가능하게 함
- **과거 날짜 체크리스트 소급 수정**: 불가로 확정. 캘린더에서 과거 날짜를 클릭해도 체크/해제는 읽기 전용 — 기록 신뢰도와 스트릭/통계 계산을 단순하게 유지하기 위함
- **빈 상태 화면 (통계 탭 / 영상 큐레이션)**: 별도 일러스트 없이 심플 텍스트 문구만 사용
  - 통계 탭(기록 없음): "아직 기록이 없어요, 루틴을 먼저 체크해보세요"
  - 영상 카테고리(해당 카테고리 영상 없음): "준비 중입니다"
- **일기 소급 수정**: 가능으로 확정. 과거 날짜의 일기도 캘린더에서 열어서 자유롭게 수정 가능 (루틴 체크와 달리 통계/스트릭 계산에 영향을 주지 않으므로 소급 수정 허용)
- **오프라인 상태 처리**: 상단 배너("오프라인 상태예요")만 표시하고 루틴 체크/저장 등 액션은 그대로 허용 (로컬에서 우선 반영 후 온라인 복귀 시 자동 동기화). 오프라인 큐 동기화 로직은 구현 난이도가 있으므로 개발 단계에서 별도 설계 필요
- **설정 화면 레이아웃**: 단일 리스트형 화면 하나로 구성 — [슬롯 4개 시간/알림 토글] → [계정: 로그아웃/탈퇴] → [앱 정보: 버전 등] 세로 나열. 항목이 늘어나면 그때 섹션/탭 분리 검토

### 4-8. LLM 자연어 입력 흐름 (신규 확정)

Todoist(실시간 파싱 하이라이트)와 영수증 스캔 앱류("AI가 초안 생성 → 사람이 확인 후 커밋")의 UX 패턴을 참고해 4단계로 확정:

```
① 입력   — 배너 탭 → 바텀시트/풀스크린 텍스트 입력창 (잔여 N/10회 표시)
② 파싱   — 정규식/키워드 사전 매칭 성공 시 "규칙 기반 처리" 배지로 즉시 결과 표시 (LLM 미호출, 횟수 차감 안 됨)
            애매한 경우만 "AI가 분석 중..." 로딩 후 LLM 호출
③ 미리보기 — 파싱 결과를 루틴 블록 카드로 표시 (초안 상태). 각 필드는 탭하면 인라인 수정 가능
④ 확정   — "이대로 추가" 버튼을 눌러야 실제 저장됨 (자동 저장 없음)
```

- **한 번의 입력으로 루틴 1개만 생성** (여러 개를 한 문장에 넣는 것은 지원 안 함) — 파싱 정확도와 정규식 사전 설계를 단순하게 유지하기 위한 결정. 여러 개를 추가하려면 입력을 반복
- ③ 미리보기 화면의 편집 폼은 4-9(루틴 블록 추가/수정 화면)와 **동일한 컴포넌트를 재사용** — 수동 추가와 AI 초안 수정이 결국 같은 필드 편집이기 때문

### 4-9. 루틴 블록 추가/수정 화면 (신규 확정 — 필드 구성)

### 4-10. 영상 큐레이션 목록 화면 (신규 확정)

- 상단 가로 스크롤 탭으로 6개 카테고리(6번 참고) 배치
- 탭 안은 2열 그리드, 카드에 썸네일 + 제목 + **채널명**(6번 확정 사항 — 필수 표시)

## 7. 수익 모델 (freemium 확정)

## 8. 개발 로드맵 (2단계 확정 — 매우 중요)

바이브 코딩으로 처음 배우면서 만드는 상황을 감안해서, **가장 어려운 결제 시스템을 검증 전에 먼저 만들지 않기로 확정**했습니다.

```
[1차 버전] — 결제 시스템 없이 무료 배포
- 블록 추가/체크, 캘린더(전체), LLM 자연어 배치(계정당 총 10회 제한),
  영상 큐레이션, 통계, 일기, 필수/선택 토글 — 전부 포함해서 완성형으로 배포
- 목적: "사람들이 이 앱을 실제로 계속 쓰는지, 어떤 기능을 제일 많이 쓰는지" 검증
- 결제/구독 로직 자체가 없음 (기간제 자동 전환 로직도 이 단계엔 넣지 않음)

        ↓ (반응 확인 후)

[2차 버전] — 검증 후 결제 시스템 추가
- 1차 데이터를 보고 어떤 기능이 진짜 "유료 가치"가 있는지 확정한 뒤 무료/유료 라인 설정
- 인앱결제(Apple/Google) 연동
- 애드몹(광고) 연동
- "2개월 무료체험 → 무료(제한) 자동전환" 로직 이 단계에서 구현
```

**핵심 원칙**: 1차 버전은 기능을 막지 않고 다 열어서 배포한다. 결제 시스템이 없으니 굳이 기능을 잠글 이유가 없고, 정확히 뭘 유료로 걸어야 하는지는 실사용 데이터로 판단하는 게 추측보다 정확하기 때문.

### 8-2. 2차 이후 확장 아이디어 — AI 루틴 피드백 (신규, 검증 필요)

경쟁 앱 "루티너리"는 실행 순간을 도와주는 가이드 타이머가 강점인데, 우리 핵심 자산(LLM 자연어 입력 + 완료기록 + 일기)은 그 방향과 다름. 실행 타이머를 따라가기보다, **AI가 쌓인 완료기록/일기를 보고 피드백을 주는 방향**이 루티너리가 구조적으로 못 하는 차별점이 될 수 있음.

- 예시: "이번 주 아침 루틴 3번 놓치셨네요, 시간을 조금 늦춰볼까요?" 같은 주간 피드백을 LLM이 생성
- **비용 통제 설계 (3번 LLM 연동 방식과 동일 철학 적용)**:
  - 실시간 호출이 아니라 **주 1회 배치**로만 생성 (사용자 행동 트리거 아님)
  - 일기 원문 전체를 보내지 않고 **완료율/스트릭 같은 구조화된 통계 요약만** 프롬프트에 포함 (입력 토큰 최소화)
  - 기존과 동일하게 **Claude Haiku** 사용, 필요 시 유료 전용 기능으로 제한해 비용을 사용자 수·매출에 비례하게 통제
- **전제조건**: 완료기록이 최소 몇 주 이상 쌓인 유저 데이터가 있어야 검증 가능 → 1차 배포 후 데이터 확보 전에는 착수하지 않음 (8번 로드맵 철학과 동일)
